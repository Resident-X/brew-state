# Hardware

Board designs and the check every one of them has to pass before it is ordered.

- `hardware/<machine>/` holds one machine's board designs, one KiCad project per board in its own folder, and the `separation-basis.yaml` they are held to.
- `hardware/tools/` holds the pre-order check, the locked-copper check used around routing, the command that renders a board's layout review views, the command that seeds the layout review's proof design, and their tests. They work for any machine.
- `hardware/proof/` holds designs committed only to prove the board tooling and the layout review: `gate-proof` for the pre-order check and `review-proof` for the layout review. They are never ordered.

A **board design** is a KiCad project file (`.kicad_pro`) together with the schematic (`.kicad_sch`) and layout (`.kicad_pcb`) of the same name beside it. The check finds every design git tracks, wherever it sits. The layout above is a convention for readers, not something the check depends on. A design is checked once git tracks it: `git add` is enough for the design's own files. The check reads a design only as the repository holds it. KiCad is given a copy of the tracked files alone, each in its place in the repository: everything in the design's folder, every sheet its schematic reaches, and every library its `sym-lib-table` and `fp-lib-table` name, wherever in the repository they sit. A library, sheet or rules file left uncommitted is therefore not used. A sheet the schematic names, a custom rules file or library table beside the project, or a library a table names, that git does not track fails the design by name. So does a library the repository cannot hold at all: one named by an absolute path, one outside the repository, or one reached through a path variable other than `${KIPRJMOD}` and those naming the libraries KiCad installs with itself (`${KICAD10_SYMBOL_DIR}`, `${KICAD10_FOOTPRINT_DIR}` and the like). Name a library from its table as `${KIPRJMOD}/` followed by its path from the design's folder. The separation basis record has to be committed exactly as it stands (see below).

KiCad is run with a configuration the check makes for the run, not the one on the machine running it. That configuration names only the libraries KiCad installs with itself, and no `KICAD…` variable from the environment reaches KiCad. A symbol or footprint whose library only one machine's own KiCad setup names, in its global library tables or its path variables, is therefore reported by KiCad as a library its configuration does not include, and fails the design under `design_library`. Put such a library in the repository and name it in the design's own table.

## What you need

Every tool is free. The check stops with an error naming any tool that is missing or too old, rather than skipping the checks that need it.

| Tool | Minimum | Where to get it |
|---|---|---|
| KiCad (its `kicad-cli`) | KiCad 10.0 | https://www.kicad.org/download/. This repository's board files are in KiCad 10's format, which older versions cannot open. |
| Python | Python 3.9 | https://www.python.org/downloads/ |
| PyYAML | PyYAML 5.1 | `pip install pyyaml`, or your system's `python3-yaml` package |
| git | git 2.11 | https://git-scm.com/downloads |
| Task | 3 | https://taskfile.dev/installation/ |
| resvg, for the layout review views only | resvg 0.47 | A prebuilt program from https://github.com/linebender/resvg/releases: the v0.47.0 release carries one for each of Windows (`resvg-win64.zip`), macOS and Linux (x86_64), and later releases carry them for macOS and Linux only. Or `brew install resvg` with Homebrew, on macOS or Linux. Or `cargo install resvg` with a Rust toolchain from https://rustup.rs/, on any operating system. It turns the views into images. The pre-order check does not need it. |
| A monospaced font for the captions, for the layout review views only | DejaVu Sans Mono, or Menlo, Consolas, Liberation Mono or Courier New | The captions are drawn in the first of these that resvg finds among the system's fonts. macOS carries Menlo and Windows carries Consolas. Elsewhere, install DejaVu Sans Mono from https://dejavu-fonts.github.io/ or your system's package of it (for example `fonts-dejavu`). Without one the command stops with `CANNOT RUN`. |

`kicad-cli` is often installed off the search path. The tasks use the variable `KICAD_CLI`, which defaults to the bare name `kicad-cli`. If it is not on your search path, set the variable to the tool's full path, either on the command line (`task hw:verify KICAD_CLI=/path/to/kicad-cli`) or in the environment. Its usual location:

| System | `kicad-cli` |
|---|---|
| macOS | `/Applications/KiCad/KiCad.app/Contents/MacOS/kicad-cli` |
| Windows | `C:\Program Files\KiCad\10.0\bin\kicad-cli.exe` |
| Linux (distribution or PPA package) | `/usr/bin/kicad-cli` |
| Linux (Flatpak) | not a file on the path: write a one-line script that runs `flatpak run --command=kicad-cli org.kicad.KiCad "$@"` and point `KICAD_CLI` at it |

`resvg` is one program, wherever it was unpacked. The view tasks use the variable `RESVG`, which defaults to the bare name `resvg`. If it is not on your search path, set it to the program's full path, for example `task hw:views RESVG=/path/to/resvg -- ...`.

## The commands

- `task hw:verify` runs the pre-order check on every board design in the repository. It exits 0 only when every design passes.
- `task hw:prove` seeds each fault the check guards against into a throwaway copy of `hardware/proof/gate-proof` as the last commit holds it, in a temporary directory outside the repository, so an uncommitted edit to the proof design is not what it proves. It requires the check to catch each fault. This command is on demand and is not part of the gate.
- `task hw:review-seed -- --seeds <file> --out <folder>` seeds known layout defects into a throwaway copy of `hardware/proof/review-proof` and writes a folder to review it blind, with the seed list apart (see [The proof designs](#the-proof-designs)). This command is on demand and is not part of the gate. It needs the same tools as `hw:views`.
- `task hw:test` runs the tests of the check itself, of the locked-copper check's four commands, of the layout review views and of the layout review proof's seeding command, against the real `kicad-cli` and `resvg`.
- `task hw:views` renders every view the layout review judges one board on (below). It needs the same tools as `hw:verify`, and resvg.
- `task hw:rules-confirm`, `task hw:copper-lock`, `task hw:copper-record` and `task hw:copper-compare` run the locked-copper check (below) on one board, before routing and around the routing round trip. They need the same tools as `hw:verify`, and read the paths given after `--` from the folder they are run in.

How a board is designed so that it passes the check and works once built, from proving its value-critical circuits, providing for its bring-up and planning its layout against the method's layout practice catalogue before placement, to its rules, its routing and the review of its finished layout, is in [`docs/board-design-method.md`](../docs/board-design-method.md).

## The locked-copper check

A board's critical nets are routed by hand and locked before an external router places the rest. The check makes sure the export, the router and the import changed none of them. It is not part of the pre-order check: it runs on one board, either side of the round trip. Only the board's own tracks, arcs, vias and zones are locked and recorded; a copper zone inside a footprint is not covered.

Every command takes the board's own project file, the one beside it with its name, which is the one KiCad opens it with, and refuses any other. The confirmation, locking and recording take the board's classes with `--class`, each once, and refuse a class the design does not define, a class KiCad places no net of the board in, and a board whose `MAINS` project variable is not exactly `present` or `none`. Confirming, locking and recording also refuse, on a board declaring `present`, a set of classes that leaves out `Mains`, and comparing fails a record whose classes leave it out. Locking, recording and comparing act on the board file, so each refuses while KiCad's lock file beside the board, `~<board>.kicad_pcb.lck`, shows it open in an editor. KiCad writes that file when an editor opens the board and deletes it when the editor closes it. It holds only a user and host name, so a lock file left behind once no KiCad process is running is stale, and is deleted.

- **Confirming the rules**, `task hw:rules-confirm -- --board <board>.kicad_pcb --project <board>.kicad_pro --class <name> [--class <name> ...]`, runs KiCad's layout rule check on a copy of the board with its project file and its own custom rules file, `<board>.kicad_dru`, with a marker rule appended to it. KiCad drops a whole rules file it cannot parse, so the marker fires only if KiCad loaded the board's rules. It fires on the items of one net, the board's net with the fewest items, so it never fills KiCad's report. The command fails, naming the rule KiCad rejects, when the marker does not fire, and fails when the board has no custom rules file. When the marker is missing from a report KiCad cut short at its limit, because the board's own assertion rules fail on that many items, it fails saying the report was cut short rather than that the rules did not load. Otherwise it lists the nets KiCad places in each class, read as [the class read](#how-a-class-is-read) reads them. It confirms that the rules file loads and that each class holds the nets intended. It does not show that each figure is the one KiCad applies, since a later rule can shadow an earlier one.
- **Locking**, `task hw:copper-lock -- --board <board>.kicad_pcb --project <board>.kicad_pro --class <name> [--class <name> ...]`, marks every track, arc, via and zone on a net in the named classes locked in the board file. It writes `(locked yes)` exactly where KiCad writes it, and changes nothing else in the file: KiCad loading and saving the locked board writes it byte for byte the same. Run it with the board closed in every editor. A board whose critical items are all locked already is left untouched.

- **Recording**, `task hw:copper-record -- --board <board>.kicad_pcb --project <board>.kicad_pro --class <name> [--class <name> ...] --record <file>`, writes every track, arc, via and zone on a net in the named classes to `<file>`. A track is recorded by its net, layer, end points and width, an arc also by its mid point, a via by its net, position, diameter, drill and layers, and a zone by its net, layers and outline. Each item also records whether it is locked. Which nets are in which class is asked of KiCad as [the class read](#how-a-class-is-read) asks it, with the board's project file and the classes its layout file carries, so assignments, patterns and layout classes all count as KiCad applies them. Recording refuses, and writes nothing, in the cases above and these: a class named twice; any item on those nets that is not locked; a `<file>` inside the board's folder or inside any other folder that holds a project file, at any depth; or a `<file>` that cannot be written. The record is a working file, and is never kept with any design. It names the board it was taken of, its classes and the nets each held.
- **Comparing**, `task hw:copper-compare -- --board <board>.kicad_pcb --project <board>.kicad_pro --record <file>`, reads the imported board against the record. It fails in these cases: a recorded item is missing, is no longer locked, or has changed in any recorded property, or a critical-class net carries an item the record does not hold. Items are matched by their recorded properties and counted, so an added copy of a recorded item is still an addition. The critical nets at comparison are every net the record names as well as every net the critical classes hold then. A class the record names that the design no longer defines fails the comparison. So a change to class membership between recording and comparing, such as a project file the import rewrote, cannot hide added copper. Copper on nets outside both is ignored. The comparison also fails, comparing nothing, when the record was taken of another board, the project file is not the board's own, or the board is open in an editor.

Each finding is one line, `<FINDING> | <item> | <detail>`, where the finding is `MISSING`, `UNLOCKED`, `CHANGED` (the detail gives each changed property as old -> new), `ADDED`, `UNDEFINED` (a recorded class the design no longer defines), `MAINS` (a board declaring mains whose record leaves out `Mains`, or a board with no valid declaration), `MISMATCH` (another board's record, or a project file not the board's own) or `OPEN` (the board is open in an editor). Recording, locking and confirming report each refusal as `REFUSED`; locking reports each item it locks as `LOCKED`; confirming reports a rules file KiCad did not load, or none, as `RULES` and a class holding no net as `EMPTY`; and confirming, locking and recording list each class's nets as `CLASS` lines. A `RESULT` line comes last. A board, project file or record that cannot be read is reported as `UNREADABLE`, and fails rather than passes. So does a KiCad run that does not load the rules asking it which nets are in which class. The exit status is 0 when the rules are confirmed, the board is locked, the record is written or the board matches it, 1 when any of those is refused or fails, and 2 when the check cannot run at all, for example because a tool is missing.

## The layout review views

`task hw:views -- --board <board>.kicad_pcb --project <board>.kicad_pro --class <name> [--class <name> ...] --out <folder>` renders, from the board's own files, every view the layout review judges the board on. It reads the paths given after `--` from the folder it is run in. Name every critical class with its own `--class`. `<folder>` must be new or empty, and outside every design's folder.

It writes these PNG images, each on a dark background:

- `layer-<layer>`: one image of each copper, mask, paste, silkscreen and edge layer, and of every other layer that holds any item, such as a keep-out or a note on a user layer.
- `assembly-top` and `assembly-bottom`: that side's fabrication, silkscreen and courtyard layers over the board edge.
- `net-<net>`: for each net in a critical class, that net's copper, each copper layer in its own colour, over a faint grey image of the whole board's copper and edge.
- `classes`: a map drawing each critical class's copper in its own colour, over the same faint image.
- `crop-<reference>`: a crop around each integrated circuit (a footprint whose reference begins with `U`) and its own decoupling parts. Its supply nets are the nets on its pads typed as power input or power output. A decoupling part is a two-pad part, not itself an integrated circuit, with its two pads on two different nets that are both supply nets of the circuit, the pattern of one rail and one return. It belongs to the one circuit sharing those nets whose nearest pad is closest to it, so a crop never names another circuit's decoupling on a shared rail as its own. A crop is framed on, and names, only its own circuit and that circuit's decoupling parts. A crop is at least 640 pixels wide, so a crop of a small circuit is widened about its centre and can take in a neighbouring circuit's parts: those are drawn but not named, so a part that neither the crop's caption nor the index names as that circuit's decoupling is not its decoupling. A circuit to which no part belongs is marked in its caption and the index as having no decoupling parts. A circuit with no pad typed as a power pin still gets its crop, marked as having no supply nets declared.
- `3d-top`, `3d-bottom` and `3d-angled`: the assembled board in three dimensions, each one image.

KiCad refills and saves the zones of a temporary copy of the whole board first. The copy keeps the design's own file names, so a text variable naming the project or the file reads as it does in place. Every model path the design's folder anchors, through `${KIPRJMOD}` or from the folder with no variable, is written out in full, so KiCad finds the same models it finds in place. A net's copper is taken from a filtered copy of that board holding only the net's tracks, arcs, vias, zones and pads. That copy is never refilled, so a pour is drawn as the whole board's copper leaves it.

Every two-dimensional view, and every tile of one, is composed in one place, which alone frames it, puts it on the dark background, draws its rule areas, names the layers it lacks and the fonts KiCad substituted, and writes its caption fields. So these hold for every two-dimensional view alike:
- A whole-board view (`layer-<layer>`, `assembly-*`, `net-<net>`, `classes`) frames everything KiCad draws on the board's plotted layers, united with the outline and the rule areas, with a millimetre to spare. A courtyard, a part or a text reaching past the outline is drawn whole rather than cut off. A crop shows only what lies within the board coordinates its caption states, and draws everything there, whichever circuit it belongs to.
- KiCad does not plot a rule area (a keep-out or placement area). The command draws each one as a bright orange dashed hatched outline on every two-dimensional view that shows one of its layers, the faint board beneath a net overlay or the class map included, wherever the view's region reaches it. It names the area in that view's caption, and in the index as a `RULE AREA` line. The three-dimensional views do not draw rule areas.
- A fabrication or courtyard layer the board does not carry is named as not carried in the caption of every view that would show it, and in the index and the report as a `LAYER` line.
- A font KiCad cannot find, whose text it draws in another, is named in every caption, the three-dimensional views' included, and in the index and the report as a `FONT` line.
- On the class map, a net in more than one critical class is drawn in the colour of the class named last, and the caption names it.

The three-dimensional views say what they leave out in their own captions, the index and the report:
- A part they draw without a model is named in their captions and in the index as a `NOT IN 3D` line: one whose model KiCad cannot find, one declaring no model, one whose model the design hides, and one marked do not populate, which the render leaves out. Each of them, whatever the reason, is also reported as a `MODEL` line in the command's report. Which parts KiCad drew a model for is judged from KiCad's three-dimensional export of the same copy (`kicad-cli pcb export glb`), not from the rendered images.
- A three-dimensional view is zoomed out until no part reaches its frame, and its caption states the zoom.

The command sets its own KiCad configuration to report in English, so it reads which fonts and models KiCad leaves out whatever language the machine is set to.

The resolution comes from the board's own design rules: three pixels across the smaller of its minimum track width and minimum clearance (Board Setup's minimums, `board.design_settings.rules.min_track_width` and `.min_clearance` in the project file). Every image is kept within a long edge of 1568 pixels and 1568 patches of 28 by 28 pixels, the size at which no reviewing model downsamples it. A two-dimensional view larger than that is cut into tiles, named `-r<row>c<column>`. Every file the command writes has a name no other of its files has, told apart even where letter case is not, as on macOS and Windows: a view whose name another file already takes, such as a net named only in a different case, has `-2`, `-3` and so on added to it. Each image carries a caption drawn into it. A two-dimensional view's caption states its layers, the colour of each layer or, on the class map, of each class, its net or class, its scale in pixels per millimetre and the board coordinates it covers. A three-dimensional view's caption states its direction and image size. The command also writes `index.txt` and `index.json`, which list every image with the same caption fields. It writes `facts.txt` and `facts.json` too, giving every net's track width range, via count, zones and classes. [`docs/board-design-method.md`](../docs/board-design-method.md#layout-review-views) gives the source of the size limit.

Class membership is asked of KiCad, as the locked-copper check asks it. The command refuses each of these by name, writing nothing:
- a project file that is not the board's own;
- a board KiCad's lock file shows open in an editor, since the views are drawn from the saved file;
- a class the design does not define, a class holding no net, or a class named twice;
- a board whose `MAINS` is not exactly `present` or `none`, or is `present` when `Mains` is not named;
- a board lacking an outer copper layer, a mask, a paste, a silkscreen, or an edge layer holding its outline;
- a board whose design rules state no minimum track width or no minimum clearance, or zero or less;
- an output folder inside any design's folder, one that already holds files, or one that is a file.

A board that cannot be read fails as `UNREADABLE`. A missing or too-old KiCad or resvg stops the command with `CANNOT RUN`. So does a resvg that finds no font to draw the captions with. The exit status is 0 when the views are written, 1 when the command is refused or its input cannot be read, and 2 when it cannot run.

## What a design must satisfy

For each design the check runs KiCad's own electrical rule check on the schematic. It also runs KiCad's own layout rule check once, on a temporary copy, with schematic parity on and every zone refilled first. KiCad does the checking itself. A router's or editor's "no violations" is never accepted in its place. A design fails on any of these:

- **Any violation KiCad reports**: electrical, layout, unconnected item, or layout-schematic disagreement. Warnings count.
- **Any check set to ignore**, in the project's severities or in a custom rule's `(severity ignore)`. This applies even when ignore is KiCad's own default for that check, as it is for `missing_courtyard` and `footprint_filters_mismatch`. Set every check to error or warning.
- **Any violation marked as excluded**, whether in the project file's exclusion lists or by a custom rule's `(severity exclusion)`. Fix the violation instead.
- **A custom rules file KiCad declines to load.** KiCad drops a whole rules file it cannot parse, without saying so, and that would leave every custom rule unchecked. The check detects this and fails the design. It then names the first rule KiCad rejects, with its line, or a missing `(version 1)` header. When no one rule can be named it says why: the file is not well-formed at a given line, or every rule loads on its own and what KiCad rejects lies in the comments between them. It finds that rule by re-running KiCad's layout check on the file's rules a few at a time, so the editor is never needed to find it. The check knows the file loaded from a marker rule it appends, which fires on the items of the layout's net with the fewest items.
- **A layout check whose report was cut short.** KiCad reports at most 199 assertion failures and drops the rest at random. A run reaching that many therefore fails the design, saying the report was cut short, because a failure of the design's own assertion rules may be among those dropped.
- **A custom rule whose name contains `pre-order check`.** Those words are reserved for the rules the check adds to the copy it checks. The rules the check recognises in KiCad's report are named afresh for every run, so no design rule can pass for one of them.
- **No mains declaration.** The project text variable `MAINS` must be `present` or `none`. A design that declares `present` must have a net in the `Mains` net class on its layout, since that is where the separation rule is enforced. A design that declares `none` may have none there.
- **Any disagreement about which nets are in `Mains`.** Three things say which nets are in the class, and each is read as KiCad itself resolves it: the layout (KiCad's answer for the layout's nets with the layout's project file and its own net classes, read as [the class read](#how-a-class-is-read) reads them), the schematic (KiCad's own netlist of it, which carries its net class directives), and the project file's net settings (its assignments by name and its patterns, which KiCad resolves for every net the layout, the schematic or an assignment names, copper or not). Every net must be in the class in all three or in none. A net in only some of them fails by name, saying which have it and which lack it. The usual fix is to save the schematic, so the project file carries its assignments, and update the layout from the schematic. A class only the layout gives a net comes from a `(net_class ...)` block that older KiCad versions wrote into the layout file, which KiCad 10 still honours.

- **Workmanship that breaks a rule of the method's workmanship area** (`WORK-` items of the layout practice catalogue in [`docs/board-design-method.md`](../docs/board-design-method.md#workmanship-work)). KiCad measures three of them: the angle at a joint between two tracks, the length of a straight run, and a via left unconnected. The design's rules file must hold a `track_angle` rule and a `track_segment_length` rule, each with no condition or the one condition `A.Type == 'Track'` and no layer, so they hold on every track; a rules file lacking either, or holding it narrowed, fails as `workmanship_rule`. KiCad reports a via unconnected or connected on one layer only, and a track end left unconnected, unaided. KiCad compares every two tracks meeting on one layer anywhere but at a pad, a branch included, so a route branches at a pad. What KiCad does not measure the check measures itself from the layout file, each against a figure the design sets as a project text variable, a plain decimal number:

  | Variable | Item | What the check measures |
  |---|---|---|
  | `WORK_DETOUR_RATIO` | `WORK-2` | Each net with tracks and two or more pads and no copper zone: the length of all its tracks and arcs, against this many times the minimum spanning tree of its pad centres in straight lines (`workmanship_detour`) |
  | `WORK_STUB_MM` | `WORK-6` | Each track end touching no pad, via, zone outline or other copper of its net: the run of track from it back to where it joins anything, against this many mm (`workmanship_stub`) |
  | `WORK_NECK_MM` | `WORK-8` | Each run of track narrower than its net class's track width (from the project file, the class KiCad ranks first for a net in several): passes only when it reaches a pad of its net and runs no more than this many mm off its net's pads' copper; a track wider than its class's width never fails (`workmanship_width`) |
  | `WORK_ANGLE_TOLERANCE_DEG` | `WORK-9`, `WORK-10` | Each straight track's direction, against a multiple of 45 degrees from the board's edges, taken from the longest straight side of the outline (`workmanship_direction`), and the angle at which a track enters a long pad, against the pad's long axis |
  | `WORK_PAD_ENTRY_RATIO` | `WORK-10` | Each track with one end on the copper of a pad at least this many times as long as it is wide and the other end off it, or running across such a pad with both ends off it: its direction there, against the pad's long axis (`workmanship_pad_entry`) |

  A variable that is missing, or not a plain decimal number within its range, fails as `workmanship_figure`, naming it. The report states, under each design's verdict line, the figure it read for each measured rule.

A design that declares `MAINS` as `present` must also:

- assign every mains-referenced net to the net class `Mains`;
- state its separation in its own custom rules file (`<design>.kicad_dru`) as **one** rule, with no `(layer ...)` and one condition written exactly `A.hasNetclass('Mains') && !B.hasNetclass('Mains')`. The rule holds both a `clearance` and a `creepage` constraint, each written `(min <n>mm)` and no less than the signed record's figures;
- be held to a signed **separation basis record**. This is the `separation-basis.yaml` in the nearest folder at or above the design. Its keys are `standard`, `supply`, `working_voltage`, `pollution_degree`, `material_group`, `environment`, `barriers`, `mains_to_low_voltage` (a mapping holding `clearance_mm` and `creepage_mm`), `accepted_by`, `accepted_on` and `synthetic`; the check compares `mains_to_low_voltage.clearance_mm` and `.creepage_mm`, in millimetres. `accepted_by` names the acceptor by the identity they record acts under in this project's requirement graph. The record fails the design if it is missing or cannot be parsed, or if a figure is missing or not a positive number. It also fails if it is unsigned: an `accepted_by` that is missing or a placeholder (`unsigned`, `tbd`, `todo`, `none`, `placeholder`, or anything in angle brackets), or an `accepted_on` that is missing, is not a `YYYY-MM-DD` date, or is later than today. A record marked `synthetic` passes only a design whose project text variable `NOT_FOR_MANUFACTURE` is `true`. The commit that adds or changes the record is its audit trail. A record that is untracked, ignored by git, staged but never committed, edited since its last commit, or deleted from the working tree therefore fails the design. A nearer uncommitted record is never passed over for a committed one further up.

The layout check enforces the signed figures, not the design's own. On the temporary copy, the record's clearance and creepage are appended to the design's rules as the last rule, in the same condition form. In KiCad the last matching rule wins, so no later or narrower rule and no net class setting can undercut it. A design that declares a stricter figure is still held only to the record's.

KiCad 10 ranks some settings above every custom rule, and the appended rule cannot outrank them. The check therefore fails them outright:

- **A local clearance override on a pad or a footprint** below the signed clearance fails, whatever net it is on. KiCad 10.0.7 applies the larger of the two items' pad or footprint overrides ahead of any custom rule. A 0.1 mm override on either a mains pad or a low-voltage pad would let low-voltage copper pass at 0.1 mm. A smaller clearance can still be written as a custom rule, which the signed rule outranks.
- **A zone's clearance** does not outrank custom rules: zones are refilled to the signed figure. A zone on a `Mains`-class net may still not declare a clearance below the signed figure.
- **A net tie joining a `Mains`-class net to any net outside the class** fails, naming the footprint and both nets. A net tie joins its nets in copper, so such a tie joins low-voltage copper to mains outright, and KiCad 10.0.7 checks no clearance between the pads it ties. A net tie may join `Mains`-class nets to one another. A pad group naming a pad its footprint does not have fails too, since which nets it joins cannot be told.

## The one form each file is read in

Wherever KiCad can answer a question, the check asks KiCad: which nets are in `Mains`, whether the rules file loaded, what a zone fills to, whether a symbol's or footprint's library is reachable. Where the check has to read a file itself, it reads it only in the one form KiCad writes, and fails any other form by name rather than guessing what KiCad would make of it:

| File | The form read | Anything else fails as |
|---|---|---|
| Custom rules (`.kicad_dru`) | Each rule has its own name, and at most one `(condition ...)`, one `(layer ...)` and one `(severity ...)`. KiCad loads a rule with two conditions and keeps only one of them, and loads two rules of one name. | `custom_rules` |
| The Mains rule in it | Exactly one condition, written exactly `A.hasNetclass('Mains') && !B.hasNetclass('Mains')`, with no other spacing; exactly one `(constraint clearance (min <n>mm))` and one `(constraint creepage (min <n>mm))`, in millimetres with no further limit; no other constraint. | `separation_rule` |
| Project file (`.kicad_pro`) | Every key once in each object; `text_variables` an object of strings; `NOT_FOR_MANUFACTURE` `true` or `false` when present; the exclusion lists lists; `net_settings.netclass_assignments` an object; `net_settings.classes` a list, each class's `track_width` a positive number or left out, when it takes the `Default` class's. Its net classes and patterns are resolved by KiCad itself. | `project_file` |
| Separation basis record | Every key once and no YAML merge key (`<<`); only the keys listed below, plus any further pair of distances for readers, a mapping holding exactly `clearance_mm` and `creepage_mm`; `mains_to_low_voltage` holding only those two; `synthetic` `true` or `false` when present. | `separation_basis` |
| Library tables (`sym-lib-table`, `fp-lib-table`) | Headed for their own kind; at most one `(version ...)`; `(lib ...)` entries each holding one `name`, one `type` of `KiCad`, one `uri`, and at most one each of `options`, `descr`, `disabled` and `hidden`; each nickname once. | `design_library` |
| Hierarchical sheets | Each `(sheet ...)` names its file in exactly one `Sheetfile` property. | `design_discovery` |

### How a class is read

The pre-order check, the locked-copper commands and the review views all learn which nets are in a net class the same way. KiCad's layout check runs on boards holding nothing but one track for each net of the layout. Each board is opened with the layout's project file and carries the `(net_class ...)` blocks the layout file holds, so KiCad applies the project file's assignments and patterns and the layout's own classes exactly as on the layout. One assertion rule per class fails on every track KiCad places in that class, and a marker rule fails on the one track laid on the back copper, which shows KiCad loaded the rules. The project file's own `Mains` nets are read the same way, without the layout's classes.

KiCad 10.0.7's command-line layout check reports at most 199 failures of one kind and drops the rest at random. A board of one track per net reports each net once per class, however much copper it carries, and the nets are split into batches small enough that a run's marker and class reports stay below that limit; the batches' answers are merged. A run whose reports still reach the limit is refused, naming the class and the limit, rather than read as complete. A correct batching never reaches it. The limit is stated once in `board_check.py`, and a test against the installed KiCad confirms it.

## The report

The report has one verdict line per design, one line under it for each measured workmanship rule's figure, one line per violation, and a result line last:

```
DESIGN | hardware/proof/gate-proof/gate-proof.kicad_pro | PASS
FIGURE | hardware/proof/gate-proof/gate-proof.kicad_pro | WORK-2 route length | WORK_DETOUR_RATIO | 1.3 times the shortest straight-line tree joining the net's pads
DESIGN | hardware/m/board/board.kicad_pro | FAIL | 1 violation
VIOLATION | hardware/m/board/board.kicad_pro | clearance | Track [/LV_A] on F.Cu, length 2.0000 mm @ (28.085, 9) mm; PTH pad 2 [/MAINS_N] of R1 @ (25.16, 10) mm | Clearance violation (rule 'pre-order check: signed separation basis' clearance 3.0000 mm; actual 2.0000 mm)
RESULT | FAIL | 1 of 2 designs failed
```

Each figure line has five fields separated by ` | `: `FIGURE`, the design, the item and what it measures, the project text variable, and the figure read with its unit. Each violation line has five fields separated by ` | `: `VIOLATION`, the design, the rule broken, where it is, and the message. The message is KiCad's own for anything KiCad found, and says what to change for anything else. The rule is KiCad's own check name (for example `clearance`, `creepage`, `pin_not_connected`, `footprint_symbol_mismatch`), or one of the check's own:

| Rule | Meaning |
|---|---|
| `design_discovery` | No design was found, a project lacks its schematic or layout, a board file is tracked without a project, or a schematic names a sheet git does not track |
| `design_unreadable` | A design file or library table cannot be opened or parsed, or KiCad cannot resolve the layout's or the project file's net classes |
| `project_file` | A setting the check reads from the project file is not in the form KiCad writes, or a key is given twice |
| `ignored_check` | A check is set to ignore, or a custom rule hides what it finds |
| `custom_rules` | KiCad did not load the design's custom rules (the location names the rule it rejects, or the line where the file stops being well-formed), the rules file is not tracked, a rule takes a name reserved for the check, two rules share a name, a rule holds a clause KiCad takes once more than once, or KiCad's report of the layout check was cut short at its limit of 199 assertion failures |
| `mains_declaration` | `MAINS` is missing or invalid, or disagrees with the layout's `Mains` net class |
| `mains_class` | The layout, the schematic and the project file's net settings do not all put the same nets in `Mains` |
| `design_library` | A library table beside the design, or a library it names, is not tracked, names a library the repository cannot hold, or is not in the form KiCad writes; or a symbol or footprint comes from a library no table the design carries names |
| `separation_rule` | The design's own Mains separation rule is missing, narrowed, incomplete, not in its one form, or below the record |
| `separation_basis` | The separation basis record is missing, unreadable, not in its one form, unsigned, not committed as it stands, or synthetic on an orderable board |
| `local_clearance_override` | A pad, footprint or Mains-class zone sets a clearance below the signed figure |
| `mains_net_tie` | A net tie joins a `Mains`-class net to a net outside the class, or names a pad its footprint does not have |
| `workmanship_rule` | The rules file lacks the `track_angle` (`WORK-4`) or `track_segment_length` (`WORK-5`) rule, or holds it narrowed by a condition or a layer |
| `workmanship_figure` | A measured workmanship rule's project text variable is missing or not a plain decimal number within its range |
| `workmanship_detour` | A net's tracks are longer than its figure allows against the shortest tree joining its pads (`WORK-2`) |
| `workmanship_stub` | A track ends free, on a run longer than its figure allows (`WORK-6`) |
| `workmanship_width` | A run of track narrower than its net class's width is not a neck within its figure of a pad (`WORK-8`) |
| `workmanship_direction` | A straight track runs off the board's edges and the 45 degrees to them by more than its figure (`WORK-9`) |
| `workmanship_pad_entry` | A track enters a long pad off its long axis (`WORK-10`) |

KiCad's own `track_angle`, `track_segment_length`, `track_dangling` and `via_dangling` findings name, in their message, the workmanship item each is.

The exit status is 0 when every design passes, 1 when any fails, and 2 when the check cannot run at all, for example because a tool is missing.

## The proof designs

`hardware/proof/gate-proof` is a deliberately tiny board. Two mains nets run through a connector and a resistor, and two low-voltage nets do the same. Its symbol and footprint libraries are carried beside it, so it needs nothing from a local KiCad installation's libraries. It is marked `NOT_FOR_MANUFACTURE=true` and carries its own synthetic `separation-basis.yaml`, and its rules file and project text variables carry the workmanship rules, each figure's source given in its rules file. It passes the check as committed, and `task hw:prove` shows each failure condition above failing on a copy of it.

`hardware/proof/review-proof` proves the layout review step of [`docs/board-design-method.md`](../docs/board-design-method.md#layout-review) rather than the check. It is a four-layer board carrying at least one part for every area of the method's layout practice catalogue: a mains terminal and a phototriac with load-side pads, a regulator, a controller with its decoupling and crystal, an exposed-pad part, a current-sense shunt and amplifier, a ferrite bead, a supply input with a transient suppressor, test points, ground planes and every floorplan region. Beside it are its floorplan and plan (`layout-plan.md`), its rules table (`design-rules.md`) and the synthetic records they read their figures from (`constraints.md` and `separation-basis.yaml`). It is laid out clean, is marked `NOT_FOR_MANUFACTURE=true`, and passes the check as committed.

`task hw:review-seed -- --seeds <file> --out <folder>` copies it into a temporary git work tree outside the repository, as `task hw:prove` copies `gate-proof`, and places layout defects in the copy, one or more for every catalogue area, each of a kind only the layout review can see. It runs the check on the copy and refuses it unless the check passes it, since the review step begins only once the check passes a board. It then writes the review folder, which must be new or empty and outside the repository, holding only what the review step gives a reviewer: the seeded copy at `hardware/proof/review-proof/` with its records, the method as written, this readme, every view `task hw:views` renders of the copy (in `views/`) and the check's report on the copy (`check-report.txt`). The design and the documents are taken as the last commit holds them. Nothing in the folder tells a seeded item or file from an unseeded one but the defect itself: each item a seed adds takes a fresh random identifier of the form KiCad gives the design's own, KiCad itself refills and saves the seeded layout so every item sits in its order and form, the design folder holds the committed design's files and no others, and every file and folder carries the same time. The seed list is written to `<file>` as JSON, giving for each seed its identifier, the catalogue item that covers it, its layer, its board position in millimetres and what it is; it is refused inside the review folder or inside any design's folder. `task hw:review-seed -- --print-prompt` prints the fixed prompt a blind review of the folder is started with, which names nothing seeded. The command prints `REFUSED` lines and exits 1 when it refuses, prints `CANNOT RUN` and exits 2 when a tool is missing, and exits 0 when the folder and the seed list are written.
