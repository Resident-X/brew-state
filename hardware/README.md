# Hardware

Board designs and the check every one of them has to pass before it is ordered.

- `hardware/<machine>/` holds one machine's board designs, one KiCad project per board in its own folder, and the `separation-basis.yaml`, `pin-allocation.yaml`, `controller-part.yaml`, `parts-specification.yaml`, `catalogue-extract.yaml` and `board-rules.yaml` they are held to, and the `derating-policy.yaml` and `pin-limits.yaml` they are held to where a design's folders hold them.
- `hardware/tools/` holds the pre-order check, the locked-copper check used around routing, the command that renders a board's layout review views, the command that renders a placed board's placement view and measures it, the command that seeds the layout review's proof design, the review kit (the command that runs a declared judged review as forks of one shared context), the layout review's caller for it, the command that writes a committed board's review folder, the critical-routing check's caller and the catalogue helpers it shares with the layout caller, the production-files check's caller and the command that writes a real order's review folder, the schematic review's caller, the command that writes a committed schematic's review folder and the command that proves the fanned-out schematic review (with the proof harness it shares with the layout review's), the command that proves the fanned-out layout review, the commands that convert and draw a board's production files and the command that seeds the proof design's production files, and their tests. They work for any machine.
- `hardware/proof/` holds designs committed only to prove the board tooling and the layout review: `gate-proof` for the pre-order check's rules, `record-keys-proof` for the keys its records carry, `review-proof` for the layout review and the ordering step's production-files check, and `circuit-review-proof` for the schematic review. They are never ordered.

A **board design** is a KiCad project file (`.kicad_pro`) together with the schematic (`.kicad_sch`) and layout (`.kicad_pcb`) of the same name beside it. The check finds every design git tracks, wherever it sits. The layout above is a convention for readers, not something the check depends on. A design is checked once git tracks it: `git add` is enough for the design's own files. The check reads a design only as the repository holds it. KiCad is given a copy of the tracked files alone, each in its place in the repository: everything in the design's folder, every sheet its schematic reaches, and every library its `sym-lib-table` and `fp-lib-table` name, wherever in the repository they sit. A library, sheet or rules file left uncommitted is therefore not used. A sheet the schematic names, a custom rules file or library table beside the project, or a library a table names, that git does not track fails the design by name. So does a library the repository cannot hold at all: one named by an absolute path, one outside the repository, or one reached through a path variable other than `${KIPRJMOD}` and those naming the libraries KiCad installs with itself (`${KICAD10_SYMBOL_DIR}`, `${KICAD10_FOOTPRINT_DIR}` and the like). Name a library from its table as `${KIPRJMOD}/` followed by its path from the design's folder. The separation basis record has to be committed exactly as it stands (see below).

KiCad is run with a configuration the check makes for the run, not the one on the machine running it. That configuration names only the libraries KiCad installs with itself, and no `KICAD…` variable from the environment reaches KiCad. A symbol or footprint whose library only one machine's own KiCad setup names, in its global library tables or its path variables, is therefore reported by KiCad as a library its configuration does not include, and fails the design under `design_library`. Put such a library in the repository and name it in the design's own table.

One KiCad run may take at most 7200 s. The limit is the constant `KICAD_TIMEOUT_S` in `hardware/tools/board_check.py`, and `hardware/tools/board_views.py` reads the same constant, so neither tool has a figure of its own. A run that outlives it fails the design as "KiCad did not finish within 7200 s", with the limit in force named, in the check and in the views command; the wait is finite, so a hung run still fails. The figure rests on a measurement made on 2026-10-31 on the main board with its ground and neutral pours and slots: KiCad's creepage test alone took about 10 minutes and the full design check 20 to 30 minutes. 7200 s is about four times the slowest of those, the margin that lets a slower machine or a denser board finish.

## What you need

Every tool is free. The check stops with an error naming any tool that is missing or too old, rather than skipping the checks that need it.

| Python | Python 3.9 | https://www.python.org/downloads/ |
| PyYAML | PyYAML 5.1 | `pip install pyyaml`, or your system's `python3-yaml` package |
| git | git 2.11 | https://git-scm.com/downloads |
| Task | 3 | https://taskfile.dev/installation/ |
| resvg, for the layout review views and for the tooling tests the build round runs | resvg 0.47 | A prebuilt program from https://github.com/linebender/resvg/releases: the v0.47.0 release carries one for each of Windows (`resvg-win64.zip`), macOS and Linux (x86_64), and later releases carry them for macOS and Linux only. Or `brew install resvg` with Homebrew, on macOS or Linux. Or `cargo install resvg` with a Rust toolchain from https://rustup.rs/, on any operating system. It turns the views into images. The pre-order check itself does not need it, but the tooling tests that the build round and the nightly run draw views, so those need it too ([When the board check runs](#when-the-board-check-runs)). |

| A monospaced font for the captions, for the layout review views and for the tooling tests the build round runs | DejaVu Sans Mono, or Menlo, Consolas, Liberation Mono or Courier New | The captions are drawn in the first of these that resvg finds among the system's fonts. macOS carries Menlo and Windows carries Consolas. Elsewhere, install DejaVu Sans Mono from https://dejavu-fonts.github.io/ or your system's package of it (for example `fonts-dejavu`). Without one the command, or the tooling tests, stop with `CANNOT RUN`. |

`kicad-cli` is often installed off the search path. The tasks use the variable `KICAD_CLI`, which defaults to the bare name `kicad-cli`. If it is not on your search path, set the variable to the tool's full path, either on the command line (`task hw:verify KICAD_CLI=/path/to/kicad-cli`) or in the environment. Its usual location:

| System | `kicad-cli` |
|---|---|
| macOS | `/Applications/KiCad/KiCad.app/Contents/MacOS/kicad-cli` |
| Windows | `C:\Program Files\KiCad\10.0\bin\kicad-cli.exe` |
| Linux (distribution or PPA package) | `/usr/bin/kicad-cli` |
| Linux (Flatpak) | not a file on the path: write a one-line script that runs `flatpak run --command=kicad-cli org.kicad.KiCad "$@"` and point `KICAD_CLI` at it |

`GERBONARA_PYTHON` is the Python of the virtual environment above. The tasks that draw layers use the variable, which defaults to the Python of the environment `task hw:gerbonara` makes and to `python3` when there is none, so only an environment made by hand needs it set, on the command line (`task hw:production-seed GERBONARA_PYTHON=/path/to/venv/bin/python -- ...`) or in the environment.

`resvg` is one program, wherever it was unpacked. The view tasks use the variable `RESVG`, which defaults to the bare name `resvg`. If it is not on your search path, set it to the program's full path, for example `task hw:views RESVG=/path/to/resvg -- ...`.

## The commands

- `task hw:verify` runs the pre-order check on every board design in the repository. It exits 0 only when every design passes. A build round runs it for a change that can matter to a board, and the nightly run of `main` runs it every night ([When the board check runs](#when-the-board-check-runs)).
- `task hw:prove` seeds each fault the check guards against into a throwaway copy of `hardware/proof/gate-proof` (or, for a fault about the keys of a record, of `hardware/proof/record-keys-proof`, for a fault about an unlisted pin of `hardware/proof/circuit-review-proof`, and for a fault about sensing clearance or ground returns of `hardware/proof/review-proof`) as the last commit holds it, in a temporary directory outside the repository, so an uncommitted edit to the proof design is not what it proves. It requires the check to catch each fault. This command is on demand: neither the build round nor the nightly runs it.
- `task hw:review-seed -- --seeds <file> --out <folder>` seeds known layout defects into a throwaway copy of `hardware/proof/review-proof` and writes a folder to review it blind, with the seed list apart (see [The proof designs](#the-proof-designs)). This command is on demand and is not part of the gate. It needs the same tools as `hw:views`.
- `task hw:production-review-folder -- --repo <repository> --commit <commit> --design <board folder> --out <folder> --work <folder> --views <folder> --placement <folder> --preview <folder> --preview-note <text> --tools <text> --command <text> ...` writes the review folder of a real order's production-files check for a judged review to read ([The production-files check by unit](#the-production-files-check-by-unit)). This command is on demand and is not part of the gate. It needs git and Python, no KiCad and no gerbonara.
- `task hw:production-seed -- --seeds <file> --out <folder>` seeds known defects into the production files of `hardware/proof/review-proof` and writes a folder to check them blind, with the seed list apart (see [The proof designs](#the-proof-designs)). This command is on demand and is not part of the gate. It needs the same tools as `hw:views`, and gerbonara.
- `task hw:test` runs the tests of the check itself, of the locked-copper check's four commands, of the layout review views, of the placement view, of the placement and critical routing history check, of the layout review record history check, of the layout review proof's seeding command, of the schematic sheet drawing command, of the review kit (its session specification and executors, answer reading, stream checks and telemetry, declaration, catalogue and shared context, planner and scheduler, merge and replicas, caller contract, contract smoke, the command and the task runner's file), of the layout review's caller, the critical-routing check's caller and the shared catalogue helpers, the production-files check's caller and its folder command, the schematic review's caller, the schematic review folder command and the schematic review proof command, the review folder command, the layout review proof command, the critical-routing review proof command and the production-files review proof command, and of the production-files conversion, rendering and seeding commands, against the real `kicad-cli`, `resvg` and gerbonara. It includes the tests that run the seeded-fault proof, so it is the whole suite, on demand.
- `task hw:test:round` runs the same tests without those that need the seeded-fault proof. It is the tooling-test part of the build round's board tier and of the nightly run ([When the board check runs](#when-the-board-check-runs)). It needs the same tools as `hw:test`: KiCad, resvg, a monospaced font and gerbonara.
  Both tasks run each test file in a process of its own, side by side, through `firmware/tools/run_tool_tests.py` (the runner the firmware tooling's tests use), from the repository root as a serial discovery run does. The runner fails when it finds no test file, names every file that fails, and writes a missing tool's `CANNOT RUN |` line once to its error output so the round reads it as a failure to look. The stage runs at most four files at once unless asked for more (`task hw:test -- --workers 10`), because the machine running the round is shared with other sessions; `task hw:test -- --workers 1` runs the files one after another. The long test files are divided by topic so no one file holds the stage: the KiCad check's tests into `test_board_check_kicad_*.py` (their shared setup and the exclusion of the seeded-fault proof in `board_kicad_fixtures.py`), the layout review views' into `test_board_views_*.py`, the history check's into `test_board_history_*.py`, the locked-copper check's into `test_locked_copper_*.py` and the review proof design's rules into `test_review_proof_rules_*.py`, each with its shared setup in a `*_fixtures.py` beside them; `test_board_kicad_division.py` holds each division to the tests the undivided file held, each in exactly one file. A test class whose tests only read a copy of a proof design and the result of checking it derives from `SharedCopy` and makes the copy and the check once, with the copy fingerprinted and verified unchanged after each test; a test that changes its copy derives from `Copy` and has one of its own.
- `task hw:reads` lists, one per line, every file the board designs git tracks read: each design's folder (with a trailing slash), its sheets, its libraries and the separation basis, pin allocation, controller part, parts specification, catalogue extract, derating policy, pin-limit, board rules and manufacturer limits records it is held to. It runs no check and needs only git and Python, no KiCad. The build round asks it which changed paths reach a board design.
- `task hw:review-run -- --caller <name> --review <folder> --out <folder>` runs a declared judged review as forks of one shared context ([The review kit command](#the-review-kit-command)). This command is on demand: neither the build round nor the nightly runs it. It needs the agent command line on the search path and logged in, and no KiCad.
- `task hw:review-smoke -- --out <folder>` runs the review kit's contract smoke, seven small probes of the installed agent command line for a few cents ([The review kit command](#the-review-kit-command)). This command is on demand: neither the build round nor the nightly runs it. It needs the agent command line on the search path and logged in, and no KiCad.
- `task hw:review-folder -- --repo <repository> --commit <commit> --design <board folder> --out <folder> ...` writes the review folder of a committed board for a judged review to read (with `--review critical-routing`, the critical-routing check's), and adds a rendered view or a text file to one it wrote ([The layout review by unit](#the-layout-review-by-unit), [The critical-routing check by unit](#the-critical-routing-check-by-unit)). This command is on demand and is not part of the gate. It needs git and Python and no KiCad.
- `task hw:review-proof -- --work <folder>` proves the fanned-out layout review on one seeded copy of `hardware/proof/review-proof` against the recorded single-reviewer runs, in one command ([The layout review by unit](#the-layout-review-by-unit)); with `--dry` it prints the plan and the predicted cost and time and starts no session. This command is on demand, spends the agent command line's usage and is not part of the gate. It needs the agent command line on the search path and logged in, and the same tools as `hw:review-seed`.
- `task hw:schematic-review-folder -- --repo <repository> --commit <commit> --design <board folder> --out <folder> --netlist <file> --netlist-command <text> --sheets <folder> --check-report <file> --number <n> --record <file> ...` writes the review folder of a committed schematic for the schematic review to read, and adds a sheet drawing, a view or a text file to one it wrote ([The schematic review by unit](#the-schematic-review-by-unit)). This command is on demand and is not part of the gate. It needs git and Python and no KiCad.
- `task hw:schematic-review-proof -- --work <folder> --seeded-repo <work tree> --seeds <file>` proves the fanned-out schematic review on one seeded copy of `hardware/proof/circuit-review-proof` against its single-reviewer run, in one command ([The schematic review by unit](#the-schematic-review-by-unit)); with `--dry` it prints the plan and the predicted cost and time and starts no session. This command is on demand, spends the agent command line's usage and is not part of the gate. It needs the agent command line on the search path and logged in, KiCad 10.0 or newer, and the seeding session's work tree and seed list.
- `task hw:critical-routing-review-proof -- --work <folder> --seeded-repo <work tree> --seeds <file>` proves the fanned-out critical-routing check on one seeded copy of `hardware/proof/method-proof` against its single-reviewer run, in one command ([The critical-routing check by unit](#the-critical-routing-check-by-unit)); with `--dry` it prints the plan and the predicted cost and time and starts no session. This command is on demand, spends the agent command line's usage and is not part of the gate. It needs the agent command line on the search path and logged in, the same tools as `hw:views`, and the seeding session's work tree and seed list.
- `task hw:production-files-review-proof -- --work <folder> --folder <production-files folder> --seeds <file>` proves the fanned-out production-files check on the seeded production files `task hw:production-seed` writes against its single-reviewer run, in one command ([The production-files check by unit](#the-production-files-check-by-unit)); with `--dry` it prints the plan and the predicted cost and time and starts no session. This command is on demand, spends the agent command line's usage and is not part of the gate. It needs the agent command line on the search path and logged in, and nothing else of its own: the folder and the seed list come from `hw:production-seed`.
- `task hw:views` renders every view the layout review judges one board on (below). It needs the same tools as `hw:verify`, and resvg.
- `task hw:placement` renders one placed board's placement view and writes its measures (below). It needs the same tools as `hw:views`.
- `task hw:sheets -- --out <folder>` draws every sheet of every board design git tracks, one image file for each sheet ([The schematic sheets](#the-schematic-sheets)). It needs KiCad and nothing else.
- `task hw:history` judges one board's placement and critical routing sections of its `layout-plan.md` against the repository's history (below). It needs git and Python only.
- `task hw:review-history` judges one board's layout review record, `layout-review.md`, against the repository's history (below). It needs git and Python only.
- `task hw:rules-confirm`, `task hw:copper-lock`, `task hw:copper-record` and `task hw:copper-compare` run the locked-copper check (below) on one board, before routing and around the routing round trip. They need the same tools as `hw:verify`, and read the paths given after `--` from the folder they are run in.

How a board is designed so that it passes the check and works once built, from proving its value-critical circuits, providing for its bring-up, reviewing its schematic against the method's circuit practice catalogue and planning its layout against the method's layout practice catalogue before placement, to its rules, its routing and the review of its finished layout, is in [`docs/board-design-method.md`](../docs/board-design-method.md).

## When the board check runs

The check runs at the same two cadences as the rest of the project's verification: in the build round, for a change that can matter to a board, and nightly on `main`. Its seeded-fault proof runs on demand.

**In the build round.** `task check:round` runs a board tier after its host and emulation tiers and before its mutation sweep. The tier is `task hw:verify`, the check on every board design, then `task hw:test:round`, the tooling tests without the seeded-fault proof's. It runs when the branch changes any of these, measured from its merge-base with `origin/main` and counting uncommitted edits and new files, as the emulation tier is measured:

- a tracked KiCad file anywhere: a name ending `.kicad_` and letters, or a `sym-lib-table`, a `fp-lib-table`, a `separation-basis.yaml`, a `pin-allocation.yaml`, a `controller-part.yaml`, a `parts-specification.yaml` or a `catalogue-extract.yaml`;
- any file under `hardware/`, the board tooling and the proof designs included;
- any file a board design reads, which `task hw:reads` lists, wherever in the repository it sits: its folder, the sheets its schematic reaches, the libraries its tables name and the separation basis, pin allocation, controller part, parts specification, catalogue extract, derating policy, pin-limit, board rules and manufacturer limits records it is held to;
- the round gate's own code, `firmware/tools/round_gate.py` and `firmware/tools/task_gate.py`;
- the task runner's definition file, `Taskfile.yml`, taken whole as the emulation tier takes it, so a firmware branch that edits it also runs the board tier.

The tier is judged on the changed paths alone. It runs when the changed paths cannot be told, as when there is no remote-tracking `origin/main`, and when `task hw:reads` fails, and it does not run on unknown changed lines alone. A branch that changes none of those paths, a firmware-only branch that leaves `Taskfile.yml` alone included, skips the tier and needs no KiCad, rasteriser or font. A KiCad design file (`.kicad_pro`, `.kicad_sch` or `.kicad_pcb`) in the working tree that git does not track fails the round, naming it, because the check finds only the designs git tracks and must not pass one it cannot see; `git add` is enough. A design file the repository's git ignore rules exclude is not a change and does not fail the round, because git is told not to track it. A missing or too-old KiCad, rasteriser or monospaced font stops the round, naming the tool, rather than skipping the tier. The round's closing lines say whether the board tier ran, why it was skipped, or that it was not reached because an earlier tier failed.

**Nightly.** `task fw:verify` declares `hw:verify` and `hw:test:round` among its gates, so the nightly run of `main` runs both, every night, whatever changed, and reports their failures as it reports every other gate's. Its hosted runner installs KiCad, the rasteriser and a monospaced font first, in `.github/workflows/nightly-verify.yml`: KiCad 10.0 from the KiCad project's own package archive for its 10.0 releases (`kicad/kicad-10.0-releases` on Launchpad) at an exact package version, the archive's signing key checked against its published fingerprint before it is trusted; resvg from the project's release archive, checked against the digest the release publishes for it; gerbonara 1.6.3 in a virtual environment of its own, read back at that version and handed to the verification as `GERBONARA_PYTHON`; DejaVu Sans Mono from the distribution's `fonts-dejavu-core` package, and PyYAML from `python3-yaml`, each at an exact version. The version, fingerprint and digest were read from those sources when they were chosen. What was not demonstrated is that the installs complete on a hosted runner: the first nightly run demonstrates that, and an install that fails there fails its own step, so it reads as provisioning and not as a board gate failing.

**On demand.** The seeded-fault proof, `task hw:prove`, is in neither the round nor the nightly. It costs two KiCad runs for every fault, and the tests that need it are separate: the full suite, `task hw:test`, includes them and stays runnable on demand, and `task hw:test:round` leaves them out. The line is drawn at one place, `hardware/tools/tests/board_kicad_fixtures.py`, which every one of the files the check's KiCad tests are divided into by topic (`test_board_check_kicad_*.py`) takes its setup from, and `test_board_kicad_division.py` holds the division to the tests the one file held, each in exactly one file. A test that needs the proof's pooled outcomes, or runs the proof itself, derives from `Proved`, and `hw:test:round` sets `BOARD_TESTS_WITHOUT_PROOF`, on which each of those files loads everything but those tests. Every other test of the check's behaviour, including each one that drives the check on a throwaway copy of the proof design directly, stays in the round and the nightly. A test in `test_board_check.py` fails if the line drifts: if any test needing the proof is in the round's tests, or any test not needing it is left out.

**Why the tooling tests need the rasteriser and a font.** The tooling tests include the layout review views' and the placement view's, which draw images and captions with resvg and a monospaced font, so the round's board tier and the nightly runner need both, as well as KiCad, whatever the change was. Each test module that needs a tool stops with a `CANNOT RUN | ...` line naming it when it is missing, which is how the round's closing lines name it.

## The locked-copper check

A board's critical nets are routed by hand and locked before an external router places the rest. The check makes sure the export, the router and the import changed none of them. It is not part of the pre-order check: it runs on one board, either side of the round trip. Only the board's own tracks, arcs, vias and zones are locked and recorded; a copper zone inside a footprint is not covered.

Every command takes the board's own project file, the one beside it with its name, which is the one KiCad opens it with, and refuses any other. The confirmation, locking and recording take the board's classes with `--class`, each once, and refuse a class the design does not define, a class KiCad places no net of the board in, and a board whose `MAINS` project variable is not exactly `present` or `none`. Confirming, locking and recording also refuse, on a board declaring `present`, a set of classes that leaves out `Mains`, and comparing fails a record whose classes leave it out. Locking, recording and comparing act on the board file, so each refuses while KiCad's lock file beside the board, `~<board>.kicad_pcb.lck`, shows it open in an editor. KiCad writes that file when an editor opens the board and deletes it when the editor closes it. It holds only a user and host name, so a lock file left behind once no KiCad process is running is stale, and is deleted.

- **Confirming the rules**, `task hw:rules-confirm -- --board <board>.kicad_pcb --project <board>.kicad_pro --class <name> [--class <name> ...]`, runs KiCad's layout rule check on a copy of the board with its project file and its own custom rules file, `<board>.kicad_dru`, with a marker rule appended to it. KiCad drops a whole rules file it cannot parse, so the marker fires only if KiCad loaded the board's rules. It fires on the items of one net, the board's net with the fewest items, so it never fills KiCad's report. The command fails, naming the rule KiCad rejects, when the marker does not fire, and fails when the board has no custom rules file. When the marker is missing from a report KiCad cut short at its limit, because the board's own assertion rules fail on that many items, it fails saying the report was cut short rather than that the rules did not load. Otherwise it lists the nets KiCad places in each class, read as [the class read](#how-a-class-is-read) reads them. It confirms that the rules file loads and that each class holds the nets intended. It does not show that each figure is the one KiCad applies, since a later rule can shadow an earlier one.
- **Locking**, `task hw:copper-lock -- --board <board>.kicad_pcb --project <board>.kicad_pro --class <name> [--class <name> ...]`, marks every track, arc, via and zone on a net in the named classes locked in the board file. It writes `(locked yes)` exactly where KiCad writes it, and changes nothing else in the file: KiCad loading and saving the locked board writes it byte for byte the same. Run it with the board closed in every editor. A board whose critical items are all locked already is left untouched.

- **Recording**, `task hw:copper-record -- --board <board>.kicad_pcb --project <board>.kicad_pro --class <name> [--class <name> ...] --record <file>`, writes every track, arc, via and zone on a net in the named classes to `<file>`. A track is recorded by its net, layer, end points and width, an arc also by its mid point, a via by its net, position, diameter, drill and layers, and a zone by its net, layers and outline. Each item also records whether it is locked. Which nets are in which class is asked of KiCad as [the class read](#how-a-class-is-read) asks it, with the board's project file and the classes its layout file carries, so assignments, patterns and layout classes all count as KiCad applies them. Recording refuses, and writes nothing, in the cases above and these: a class named twice; any item on those nets that is not locked; a `<file>` inside the board's folder or inside any other folder that holds a project file, at any depth; or a `<file>` that cannot be written. The record is a working file, and is never kept with any design. It names the board it was taken of, its classes and the nets each held.
- **Comparing**, `task hw:copper-compare -- --board <board>.kicad_pcb --project <board>.kicad_pro --record <file>`, reads the imported board against the record. It fails in these cases: a recorded item is missing, is no longer locked, or has changed in any recorded property, or a critical-class net carries an item the record does not hold. Items are matched by their recorded properties and counted, so an added copy of a recorded item is still an addition. The critical nets at comparison are every net the record names as well as every net the critical classes hold then. A class the record names that the design no longer defines fails the comparison. So a change to class membership between recording and comparing, such as a project file the import rewrote, cannot hide added copper. Copper on nets outside both is ignored. The comparison also fails, comparing nothing, when the record was taken of another board, the project file is not the board's own, or the board is open in an editor.

Each finding is one line, `<FINDING> | <item> | <detail>`, where the finding is `MISSING`, `UNLOCKED`, `CHANGED` (the detail gives each changed property as old -> new), `ADDED`, `UNDEFINED` (a recorded class the design no longer defines), `MAINS` (a board declaring mains whose record leaves out `Mains`, or a board with no valid declaration), `MISMATCH` (another board's record, or a project file not the board's own) or `OPEN` (the board is open in an editor). Recording, locking and confirming report each refusal as `REFUSED`; locking reports each item it locks as `LOCKED`; confirming reports a rules file KiCad did not load, or none, as `RULES` and a class holding no net as `EMPTY`; and confirming, locking and recording list each class's nets as `CLASS` lines. A `RESULT` line comes last. A board, project file or record that cannot be read is reported as `UNREADABLE`, and fails rather than passes. So does a KiCad run that does not load the rules asking it which nets are in which class. The exit status is 0 when the rules are confirmed, the board is locked, the record is written or the board matches it, 1 when any of those is refused or fails, and 2 when the check cannot run at all, for example because a tool is missing.

## The layout review views

`task hw:views -- --board <board>.kicad_pcb --project <board>.kicad_pro --class <name> [--class <name> ...] --out <folder>` renders, from the board's own files, every view the layout review judges the board on. It reads the paths given after `--` from the folder it is run in. Name every critical class with its own `--class`. `<folder>` must be new or empty, and outside every design's folder. The review judges the board on its [placement view](#the-placement-view) too, which `task hw:placement` renders into a folder of its own.

It writes these PNG images, each on a dark background:

- `layer-<layer>`: one image of each copper, mask, paste, silkscreen and edge layer, and of every other layer that holds any item, such as a keep-out or a note on a user layer.
- `assembly-top` and `assembly-bottom`: that side's fabrication, silkscreen and courtyard layers over the board edge.
- `net-<net>`: for each net in a critical class, that net's copper, each copper layer in its own colour, over a faint grey image of the whole board's copper and edge. A net's view is written only as the tiles of the whole-board grid that hold some of the net's copper: a track or arc with its width, a via, a pad, a copper shape on the net, or a zone's fill, on any copper layer, as KiCad plotted it of a copy holding only that net. A tile that holds a corner or an edge of one of those is written, so a tile may be written that shows none of the net's pixels, never the reverse. A tile of the grid that holds none of the net's copper is not written, and the net's other tiles keep the names, board regions, scale and faint whole-board background they have when every tile is written. A net with no copper on any copper layer writes no tile. Each of its captions states how many tiles of the net's grid are left out.
- `classes`: a map drawing each critical class's copper in its own colour, over the same faint image.
- `crop-<reference>`: a crop around each integrated circuit (a footprint whose reference begins with `U`) and its own decoupling parts. Its supply nets are the nets on its pads typed as power input or power output. A decoupling part is a two-pad part, not itself an integrated circuit, with its two pads on two different nets that are both supply nets of the circuit, the pattern of one rail and one return. It belongs to the one circuit sharing those nets whose nearest pad is closest to it, so a crop never names another circuit's decoupling on a shared rail as its own. A crop is framed on, and names, only its own circuit and that circuit's decoupling parts. A crop is at least 640 pixels wide, so a crop of a small circuit is widened about its centre and can take in a neighbouring circuit's parts: those are drawn but not named, so a part that neither the crop's caption nor the index names as that circuit's decoupling is not its decoupling. A circuit to which no part belongs is marked in its caption and the index as having no decoupling parts. A circuit with no pad typed as a power pin still gets its crop, marked as having no supply nets declared.
- `3d-top`, `3d-bottom` and `3d-angled`: the assembled board in three dimensions, each one image.

KiCad refills and saves the zones of a temporary copy of the whole board first. The copy keeps the design's own file names, so a text variable naming the project or the file reads as it does in place. Every model path the design's folder anchors, through `${KIPRJMOD}` or from the folder with no variable, is written out in full, so KiCad finds the same models it finds in place. A net's copper is taken from a filtered copy of that board holding only the net's tracks, arcs, vias, zones and pads. That copy is never refilled, so a pour is drawn as the whole board's copper leaves it.

Every two-dimensional view, and every tile of one, is composed in one place, which alone frames it, puts it on the dark background, draws its rule areas, names the layers it lacks and the fonts KiCad substituted, and writes its caption fields. So these hold for every two-dimensional view alike:
- A whole-board view (`layer-<layer>`, `assembly-*`, `net-<net>`, `classes`) frames everything KiCad draws on the board's plotted layers, united with the outline and the rule areas, with a millimetre to spare. A courtyard, a part or a text reaching past the outline is drawn whole rather than cut off. A crop shows only what lies within the board coordinates its caption states, and draws everything there, whichever circuit it belongs to.
- KiCad does not plot a rule area (a keep-out or placement area). The command draws each one as a bright orange dashed hatched outline on every two-dimensional view that shows one of its layers, the faint board beneath a net overlay or the class map included, wherever the view's region reaches it. It names the area in that view's caption, and in the index as a `RULE AREA` line. The three-dimensional views do not draw rule areas.
- A fabrication or courtyard layer the board does not carry is named as not carried in the caption of every view that would show it, and in the index and the report as a `LAYER` line.
- A font KiCad cannot find, whose text it draws in another, is named in every caption, the three-dimensional views' included, and in the index and the report as a `FONT` line.
- On the class map, a net in more than one critical class is drawn in the colour of the class named last, and the caption names it.

The three-dimensional views say what they leave out in their own captions, the index and the report:
- A part they draw without a model is named in their captions and in the index as a `NOT IN 3D` line: one whose model KiCad cannot find, one declaring no model, one whose model the design hides, and one marked do not populate, which the render leaves out. Each of them, whatever the reason, is also reported as a `MODEL` line in the command's report. Which parts KiCad drew a model for is judged from KiCad's three-dimensional export of the same copy (`kicad-cli pcb export glb`), not from the rendered images. KiCad builds differ in the status that export ends with when a model is missing: one that exits non-zero after writing a readable file is used, and the index and the report state the status and what KiCad said in a `3D EXPORT` line, while a non-zero status with no file, an empty file or one that cannot be read stops the command, as a non-zero status from any other KiCad command does.
- A three-dimensional view is zoomed out until no part reaches its frame, and its caption states the zoom.
- The KiCad 10.0.7 build the hosted Ubuntu runner installs does not read a VRML (`.wrl`) model when it writes the three-dimensional export, though the macOS build does. A part whose only model is a `.wrl` file is therefore reported on that runner as one KiCad drew no model for, in the `NOT IN 3D` and `MODEL` lines above. Give a part a STEP model where the same view must come out on both.

The command sets its own KiCad configuration to report in English, so it reads which fonts and models KiCad leaves out whatever language the machine is set to.

The resolution comes from the board's own design rules: three pixels across the smaller of its minimum track width and minimum clearance (Board Setup's minimums, `board.design_settings.rules.min_track_width` and `.min_clearance` in the project file). Every image is kept within a long edge of 1568 pixels and 1568 patches of 28 by 28 pixels, the size at which no reviewing model downsamples it. A two-dimensional view larger than that is cut into tiles, named `-r<row>c<column>`. Every file the command writes has a name no other of its files has, told apart even where letter case is not, as on macOS and Windows: a view whose name another file already takes, such as a net named only in a different case, has `-2`, `-3` and so on added to it. Each image carries a caption drawn into it. A two-dimensional view's caption states its layers, the colour of each layer or, on the class map, of each class, its net or class, its scale in pixels per millimetre and the board coordinates it covers. A three-dimensional view's caption states its direction and image size. The command also writes `index.txt` and `index.json`, which list every image with the same caption fields, and for each critical net its grid: a `NET TILES` line in the text and an entry of `net_tiles` in the JSON, giving the net, the rows and columns of its grid, each tile written by row and column with its file and the board region it covers, the number of tiles left out because none of the net's copper is in them (none left out when every tile is written), and, for a net with no copper on any copper layer, that reason with no tile written. The command's report also names a net with no tile written. It writes `facts.txt` and `facts.json` too, giving every net's track width range, via count, zones and classes. [`docs/board-design-method.md`](../docs/board-design-method.md#layout-review-views) gives the source of the size limit.

Class membership is asked of KiCad, as the locked-copper check asks it. The command refuses each of these by name, writing nothing:
- a project file that is not the board's own;
- a board KiCad's lock file shows open in an editor, since the views are drawn from the saved file;
- a class the design does not define, a class holding no net, or a class named twice;
- a board whose `MAINS` is not exactly `present` or `none`, or is `present` when `Mains` is not named;
- a board lacking an outer copper layer, a mask, a paste, a silkscreen, or an edge layer holding its outline;
- a board whose design rules state no minimum track width or no minimum clearance, or zero or less;
- an output folder inside any design's folder, one that already holds files, or one that is a file.

A board that cannot be read fails as `UNREADABLE`. A missing or too-old KiCad or resvg stops the command with `CANNOT RUN`. So does a resvg that finds no font to draw the captions with. The exit status is 0 when the views are written, 1 when the command is refused or its input cannot be read, and 2 when it cannot run.

## The placement view

`task hw:placement -- --board <board>.kicad_pcb --project <board>.kicad_pro --out <folder>` renders, from a placed board's own files, routed or not, the view a placement is judged on, and writes the placement's measures beside it. It reads the paths given after `--` from the folder it is run in. `<folder>` must be new or empty, and outside every design's folder, so it is never the folder `task hw:views` wrote. The floorplan is read from the region table of the `layout-plan.md` beside the board ([`docs/board-design-method.md`](../docs/board-design-method.md#1-draw-the-floorplan)): each region's rectangles, or `none`, and the reference designators its Parts column lists.

A net's **connections** are the minimum spanning tree over the centres of its pads, the shortest set of straight lines pad to pad that joins them all, taken from the same board geometry the pre-order check's detour measure (`WORK-2`) uses. A net with one pad has none. Copper already laid is ignored, in the image and in the measures, so a board measures the same before routing and after it, and a placement changed on a routed board is measured again the same way.

It writes these files:

- `placement`: a PNG of the board's parts, drawn from a copy of the board holding none of its tracks, arcs, vias or zones: the pads of both outer copper layers, each side's fabrication, courtyard and silkscreen layers, and the edge. Over them each net's connections are drawn as bright green straight lines between the pads they join, and each floorplan region's rectangles as cyan dashed outlines with the region's name; a region recorded as `none` has no rectangle. Rule areas are drawn as the views draw them. It takes the layout review views' form: a dark background, a caption drawn into the image stating its layers and their colours, the connections' colour, each region and its bounds, its scale and the board coordinates it covers, three pixels across the smaller of the board's minimum track width and minimum clearance, and tiles named `-r<row>c<column>` when it is larger than a long edge of 1568 pixels or 1568 patches of 28 by 28 pixels. A font KiCad substitutes and a layer the board does not carry are named in its caption, the index and the report, as the views name them.
- `index.txt` and `index.json`: every image of the view with its caption, the resolution, and the names of the measures' two files.
- `measures.txt` and `measures.json`: the placement's measures, the same in both:
  - the total length of the connections, and each net's length, with how many pads it joins;
  - the crossings, in total and by net. A crossing is two segments of different nets that intersect, touch or overlap, so a connection passing through another net's pad centre crosses that net's connection from the pad. Segments of one net are never counted against each other;
  - every part outside its regions. A part's extent is the rectangle along the board's axes that bounds its courtyard, or its pads where it has no courtyard. A part is outside when that extent is not covered by the union of the rectangles of the regions it is listed in, so a part listed in two regions, such as an isolator whose pins lie either side of the mains boundary, is outside only when it leaves both. A part listed in no region is outside.
  - each region as it was read, with its bounds and parts.

In `measures.txt`, the lines are `LENGTH | total | <mm> mm`, `CROSSINGS | total | <n>`, `OUTSIDE | total | <n>`, one `NET | <net> | <n> pads | length <mm> mm | <n> crossings` per net, one `OUTSIDE | <reference> | <where it is listed and where its extent lies>` per part outside, and one `REGION | <name> | <bounds> | <parts>` per region. The command's report gives an `OUTSIDE` line for each part outside, a `MEASURES` line with the totals, a `RESOLUTION` line and a `RESULT` line last.

Its refusals are the views' own. It refuses each of these by name, as a `REFUSED` line, writing nothing:
- a project file that is not the board's own;
- a board KiCad's lock file shows open in an editor, since the view is drawn from the saved file;
- a board whose design rules state no minimum track width or no minimum clearance, or zero or less, since the resolution comes from them;
- an output folder inside any design's folder, one that already holds files, or one that is a file.

It stops, writing nothing, with an `UNREADABLE` line naming what it could not read, when the `layout-plan.md` beside the board is missing or holds no floorplan table with a Parts column and a separator row of dashes under its header; when a region row cannot be read: a cell count other than its header's, bounds neither `none` nor rectangles `(x1, y1)–(x2, y2)` of some area, or a Parts entry that is not one reference designator, such as a range; when two region rows carry the same region name, compared as exact strings; when a part is listed in a region recorded as `none`; when a listed part is not on the board; and when a footprint on the board has no reference, or two or more share one, naming each such reference and how many footprints carry it, since the floorplan lists every part by a reference of its own. A board that cannot be read fails as `UNREADABLE` too. A missing or too-old KiCad or resvg, or a resvg that finds no font to draw the caption with, stops the command with `CANNOT RUN`. It needs the same tools as `task hw:views`: KiCad 10.0 or newer, resvg 0.47 or newer and a monospaced font for the caption ([What you need](#what-you-need)). The exit status is 0 when the view and its measures are written, 1 when the command is refused or its input cannot be read, and 2 when it cannot run.

## The schematic sheets

`task hw:sheets -- --out <folder>` draws every sheet of every board design git tracks, so a reader can follow a schematic on paper or a screen without opening an editor. A reader who wants the drawings needs the design tool this repository names: KiCad 10.0 or newer, whose command-line tool draws them, and nothing else (no rasteriser, no font and no second program). The drawings are not committed, so a drawing never differs from the schematic it shows; they are made when wanted.

It finds the designs as the pre-order check does, every KiCad project file git tracks, wherever it sits, and copies each design's tracked files, its sheets and libraries included, into a scratch copy of the repository before KiCad draws it, so a drawing shows the design as the repository holds it and not a file left lying beside it. It writes nothing into the repository. `<folder>` must be new or empty, and outside every design's folder. Inside it each design has a subfolder that follows the design's place in the repository, holding one SVG file for each sheet: the root sheet is named for the design (`<design>.svg`) and a sheet below it for the design and its own name (`<design>-<sheet name>.svg`). Each file written is printed as a `SHEET` line, each design as a `DESIGN` line, and the last line is `RESULT`.

It fails a design it cannot draw, naming the design and what is wrong: a project whose schematic is not tracked, a sheet that cannot be read, or a drawing KiCad does not make. It fails when the repository tracks no design, since a command that finds nothing to draw has not shown that anything can be. It refuses an output folder inside a design's folder, one that already holds files, and one that is a file. A missing or too-old KiCad stops it with a `CANNOT RUN` line naming `kicad-cli`. The exit status is 0 when every sheet of every design is written, 1 when a design cannot be drawn or the command is refused, and 2 when it cannot run.

## The review kit command

`task hw:review-run -- --caller <name> --review <review folder> --out <output folder>` (`hardware/tools/review_run.py`, which runs `hardware/tools/review_kit/command.py`) runs a declared judged review as forks of one shared context. A review divides into units that do not depend on one another. The command builds one shared context holding every artefact any unit needs, starts it once as a session that judges nothing, then starts a fork of it for each group of units and each replica, the forks running together and no more of them at once than the bound, and merges the replicas with no model: a checklist item fails when any replica fails it. Nothing of any board is in the kit; what a review is belongs to its caller.

It is on demand and in neither the build round nor the nightly ([When the board check runs](#when-the-board-check-runs)). It needs the agent command line on the search path and logged in, Python 3.9 or newer, and no KiCad. The command line's name is read from one environment variable, `REVIEW_KIT_AGENT`, which is `claude` when it is unset, so the tests stand a stub in its place. It counts as logged in only when `auth status` exits 0 and prints a JSON object whose `loggedIn` is `true`. A command line that is missing, not logged in, or that stops being either during the run, stops the command with a line beginning `CANNOT RUN` and exit status 2.

**Inputs.**

- `--caller <name>` is a Python module `review_caller_<name>` in the folder `--callers` names (the tools folder when it is left out). It must supply `declaration` (a path, a mapping, or a function of the review folder returning the mapping), `checks(tables)` (the problems in the merged tables, as a list of text; none when they hold) and `render(review_folder, tables)` (the files of the rendered record, as a mapping of file name to text). It may supply `retrieval` (`True`, or the tools granted beside `Read`, `Glob` and `Grep`; `WebFetch` is the one retrieval tool), `checklist`, `prompt(unit, review_folder)`, `place(row)`, `round_label`, `earlier_findings`, `first_finding`, `bound` (the most sessions at once, a whole number of 1 or more; the plan's fork count when it is absent, and never more than that; `--bound` overrides it), `fail_verdict` (which verdict of the declared verdict tables is the caller's fail verdict, held as `fail` is: `fail` when it is absent, naming `fail` is the same as naming none; a name no verdict table carries is refused before any session starts, the refusal naming it and each verdict table with its verdicts; a name that is not text or is blank, or is `cannot judge`, is refused when the caller loads, naming the attribute) and `replica_policy` (the variants the replicas take in turn, each with an `id`, an `item_order`, a `view_order`, a `framing`, a `terse` flag, a `seed` and an optional full `model` id, and the number of replicas for `low`, `normal` and `high` stakes, which are one, two and three unless it says otherwise).
- The declaration is a JSON file holding `artefacts` (each a `kind` of `text`, `image` or `extract`, a `source` inside the review folder and, for an extract, a `producer`), `templates` (prompt text with named slots), `units` (each with its `items`, `template`, `needs`, `couples_with`, `expected_output_tokens`, `stakes` and `values`), `schema` (the result tables, with a key, columns and verdict sets, and the findings table; a table's `key` is one column name, or a list of column names of which the first is the item, and a verdict table keyed by several columns gives one verdict to each combination of its key cells for each item of the unit, which is merged any-fail and proved per combination), `deny` (patterns an artefact may not match: it is enforced when artefacts are admitted, so a declared artefact matching one refuses the run before any session starts) and `budget` (`wall_s`, `usd`, `context_tokens` and `tree_saving_usd`) and, optionally, `added_during_round` (path patterns relative to the review folder, a `*` crossing `/`, for what the caller adds to the folder during the round; none may match a declared artefact, which is refused at load). The folder hash recorded at the first run and recomputed at a rerun leaves those paths out, so a rerun accepts a change confined to them and refuses any other change to the folder, and refuses a declaration that lists other patterns than the recorded run. The patterns are matched with case folded, against each artefact's path as it resolves on disk with links followed (and `..` removed) as well as against the path as declared, and a pattern that would match an artefact by any of them, including through a link to a directory, is refused at load. A pattern may also cover files that are not artefacts but that a reviewer can read by tool, such as a KiCad file; a rerun then accepts a change to them, and what the reviewers see changes with it.
- `--review <folder>` is the review folder the sessions read. It must exist and be outside the repository. `--out <folder>` is the output folder, outside the repository and apart from the review folder (neither inside it nor containing it).
- `--bound N` is the most sessions at once; it defaults to the caller's `bound` where the caller declares one, else to one for every fork the plan has. `--replicas N` makes every unit take N replicas in place of the number its stakes give. `--model <full model id>` is the model every session uses, and the agent command line's own when it is left out. `--rerun <unit>` (repeat for each unit) runs the named units again against a record already in the output folder. `--format text|json` chooses the report.

The model flag takes a full model id, such as the one the start report gives, because each session's start report is compared with the specification and an alias that the start report gives under another name is refused.

**Outputs.** The output folder holds `plan.json` (the plan), `record.json` (the run's record: the plan, every node with its role, parent, group, replica, attempt and figures, every attempt of every unit, each unit's state, the merged tables, the figures of the last run, the runs made, and the keys `rendered` and `not_this_merge`), `streams/` (every session's stream exactly as the command line printed it, with the specification and message hashes that key it), the files the caller rendered, and `run.lock` while a run is in it. The files a caller renders must each be one plain name of ASCII letters, digits, full stops, underscores and hyphens, not one the kit uses, and are written after the merge; a name already in the output folder is replaced only when an earlier merge wrote it and it is still a regular file. A file an earlier merge wrote that a later merge does not render is left in place and named under `not_this_merge`. The rendered files are written before the record, so after a failed record write the files remain with no record naming them and read as foreign: they refuse a rerun's merge until they are removed. Remove the files the failed run rendered from the output folder, or run into a new output folder, and run again. The exit status is 0 when the merged record is written, 1 when the command refuses or a unit fails, and 2 when the agent command line is missing or not logged in.

**A rerun.** `--rerun u1` starts the shared context again with the identical bytes (the cache is hit inside its lifetime, and otherwise the shared context is written once, and the record says whether a new shared context was started), runs the groups that hold the named units, replaces their results and merges again. It is refused for a unit the review does not have, for leaving out a unit whose last run failed, for a review folder whose hash differs from the recorded one (the refusal names the first path that differs), and when the declaration now gives other groups, another session specification or another shared context than the recorded run.

**A replica on another model.** A variant of the `replica_policy` that names a model other than the review's has a shared context and a session specification of its own, since the cache cannot be shared across models. The command starts every shared context before any fork, and each replica forks from the context of its own model. The report lists those contexts as `CONTEXT` lines.

**Repairs and prices.** A repaired answer, from the turn about a first answer's `cannot judge` or from a repair of a local problem, that clears a fail the first answer raised on a checklist item (by passing it or leaving it out) carries a local problem naming the item, so the first answer stands over it and a repair never clears a fail; a row of the first answer that was itself invalid (an item off the checklist, or two items in one cell) is not a fail to carry. The turn about a `cannot judge` advises retrieving a document only when the caller grants the retrieval tool, and otherwise asks the session to keep the `cannot judge` and name the view or document it needs. The small-tier prices were fitted from one recorded run and checked against two later ones; a run with a different thinking volume is mispredicted, because the generated-token price absorbs that volume. A model with no entry in the price table is priced at the default, and the plan says so in a `NOTE` line (`--dry` of the layout proof prints a `WARNING` line).

**The report.** It is printed as text, or with `--format json` as one JSON document holding the same facts. Lines begin `RUN`, `NOTE`, `REFUSED`, `CANNOT RUN`, `AGENT`, `PLAN`, `GROUP`, `CONTEXT`, `PREDICTED`, `SESSION`, `TOTAL`, `AGAINST PREDICTED`, `CHECK FAILED`, `UNIT`, `RERUN`, `SAME PLACE`, `RENDERED`, `NOT THIS MERGE`, `FILE`, `TABLE`, `ROW` and `RESULT`, and every fact of the JSON document is in them. It records the plan (the groups and their replicas, the forks, the bound, the size and prefix hash of the shared context, the session specification's digest, the predicted cost and time, the saving a tree of shared contexts would make against its threshold, the agent command line's version and the tool commit), each session's own figures (cost, API time, wall time, turns, calls, tokens read from the cache, written to it, fresh and generated, and the cache read of its first call, with a fork's cost and time taken as its reported cumulative figures less its parent's), the run's figures (the sharing ratio, the tokens written in more than one session and the critical-path time), the predicted cost and time against the actual with their deviations, the checks that failed (a fork that read less from the cache than its parent's prefix holds, a unit that still has a problem on its last attempt, a session whose figures cannot be told, and the places where two findings land), the units' states, and the files rendered and left from an earlier merge. For a rerun the figures are those of the sessions that rerun started, and the prediction is for the groups it ran.

**What a start report cannot show or exclude.** Each session's start report is checked against the specification for the tools granted, the model, no MCP server, no skills, no slash commands, no plugin from outside the agent command line itself and the review folder as the working directory. The start report carries no system prompt, so the command does not see it; the contract smoke checks that a fork carries its root's system prompt. A source the installed command line cannot exclude is not hidden, and the report cannot show or exclude it: the built-in plugins and agents load, the account email reaches the first message, and when the review folder is inside a git work tree the branch, the status and the recent commit subjects reach the first message too, so give a review folder outside any work tree. Whether the hooks and memory exclusions took cannot be seen in the start report, which does not list them. The sessions hold the read tools, and no path-scoped rule limits them, so a fork that is given or guesses an absolute path can read a file outside the shared context, the output folder included (the other units' verdicts and the streams are there): keep the output folder apart from the review folder, do not show its path to a session, and do not put a file a session must not read in the review folder, since `deny` guards declared artefacts only.

**When it refuses.** Each cause is one line beginning `REFUSED` or `CANNOT RUN` that names the cause and what to do, and a `RESULT` line comes last. Nothing is started for a refusal made before the run, and the output folder is not made.

| The line says | Cause | What to do |
| --- | --- | --- |
| `the command line cannot be used` | A flag is missing or unknown. | run with --help for the options |
| `does not exist` | The review folder is not a folder. | give the folder the review's starter wrote |
| `could read the design as committed` | The review folder is inside the repository. | give a review folder outside it |
| `is a file` | The output folder is a file. | give a new or empty folder |

**A lock left by a killed run.** A run holds `run.lock` in the output folder while it is in it, and the lock records the identifier of the process that holds it. A lock whose process no longer exists on this machine is taken over: the command removes it, goes on, and reports the takeover on a `NOTE` line. The takeover is by process identifier, so it assumes the run that left the lock was on this machine.

## The layout review by unit

A layout review round can be judged by unit, as the method's [layout review step](../docs/board-design-method.md#layout-review) says: one reviewer for each set of coupled areas of the layout practice catalogue, one for the board's own items and one for the comparison with the plan and the free pass, each a fork of one shared context that [the review kit's command](#the-review-kit-command) builds from the review folder, two reviewers of each so that any fail stands, and the units merged with no model into one round of the board's review record. Three commands carry it: the folder command that writes the review folder, the layout caller that the review kit's command runs (`task hw:review-run -- --caller layout --review <review folder> --out <output folder>`), and the proof command that shows the fanned-out form finds what the recorded single reviewer found. All three are on demand and in neither the build round nor the nightly ([When the board check runs](#when-the-board-check-runs)).

**The folder command.** `task hw:review-folder -- --repo <repository> --commit <commit> --design <board folder from the repository's root> --out <new folder> --views <views folder> --placement <placement folder> --check-report <file> --number <n> --kind full|narrow --view-command <text> --check-line <line>` (`hardware/tools/review_folder.py`; repeat `--view-command` and `--check-line` for each) writes the folder a judged review reads, outside the repository. It needs git and Python, no KiCad and no model; what it is given is what the round's first step produces: the folder `task hw:views` rendered, the folder `task hw:placement` rendered, the pre-order check's report from `task hw:verify`, and the commit that holds the board. The folder holds the board's design files as the commit holds them, its plan, its rules table and the records those name, the method and this readme (from this repository, or from `--documents-repo` and `--documents-commit`), the views in `views/`, the placement view in `placement/`, the check's report in `check-report.txt`, two extracts written from the commit (`layout-facts.txt`, the positions, pads, segments, vias and zones of the board file, so that a reviewer reads a distance from the extract and opens no view again, and `method-extract.md`, the three sections of the method a layout review needs) and `round.json`, the round file. It holds no session or notes file, no other file the commit does not hold and, for a first round, no review record; for a later round it holds the earlier rounds of the board's `layout-review.md` as the commit holds them, since a verdict row may cite a finding an earlier round closed by a reason. Every file and folder carries one time.

The round file holds the round's own fields, which the merge has no model to write: the round's number, its kind, the commit judged (taken from `--commit`), the commands the views were rendered with (`--view-command`) and the pre-order check's lines (`--check-line`: the board's `DESIGN` line and every `FIGURE` and `VIOLATION` line under it). A narrow round also gives each listed item with the reason the changed regions touch it (`--item ITEM=reason`), its changed regions named from the fix commits (`--region`) and the line saying why every other item is not judged (`--others`); a full round gives none of them. The set of fields is a parameter: `--round-fields number,kind,commit,views,check` is the layout review's, and a review whose round has no kind or check lines names a shorter set. A missing or malformed field, a folder inside the repository or either repository, a folder that is not new or empty, a commit that does not hold a board or is not in the repository, views, a placement view or a report that is missing, a documents repository that lacks the method or the notes, and a round after the first whose commit holds no earlier round of the record each refuse the command, naming the cause and writing nothing (`REFUSED` lines and exit status 1; 2 when git is missing); `--json` prints the same facts as one JSON document.

`task hw:review-folder -- --add-view <review folder> --view <file> --view-command <text> --cannot-judge-item <item> --cannot-judge-why <text>` resolves a `cannot judge`. A reviewer holds read tools and cannot render, so whoever started the round renders the view the item's Why asks for and adds it with this mode, which puts the file in `added-views/` and records the item, its Why, the view and the command that rendered it in `added-views/resolutions.json`. Nothing of the shared context changes and the round file is not rewritten, so the kit's `--rerun`, which refuses a changed review folder except for the paths the declaration lists as added during the round, accepts the folder; whoever started the round then runs that unit again with `--rerun`. The merged row, built from the resolution and the re-run's verdict, records the `cannot judge`, the view and the verdict reached, and the added view is folded into the round's Views field. It refuses a view that does not exist, a name already added and a folder the command did not write.

`task hw:review-folder -- --add-document <review folder> --document <text file> --source <where the figure comes from> --cannot-judge-item <item> --cannot-judge-why <text>` resolves a `cannot judge` whose Why asks for a document the folder lacks and the plan gives no address to fetch it from, such as a datasheet's package drawing. Whoever started the round writes the figure or passage into a text file of at most 64 KiB and adds it with this mode, which puts it in `added-documents/` and records the item, its Why, the document and its source, as `kind` `document`, in the same `added-views/resolutions.json` (an entry with no `kind` is a view). The declaration lists `added-documents/*` as well as `added-views/*` among the paths added during the round, so `--rerun` accepts the folder, and the unit's prompt on the re-run names the document and its source. The merged row records the `cannot judge`, the document and the verdict reached; a document has no rendering command, so the Views field holds views alone. It refuses a file that does not exist, is not UTF-8 text or is over 64 KiB, an empty or multi-line source, a name already added, an item the folder's checklist does not hold and a folder the command did not write. The review seeding command's copy of a commit's files (`copy_commit` in `review_seed.py`) is the folder command's copy, generalised to take a repository, a commit and a design, with the documents optionally from a second repository; rendering stays in the seeding command.

**The layout caller.** `hardware/tools/review_caller_layout.py` is the caller `--caller layout` names, run on a review folder the folder command wrote. Its units are one for each area heading of the catalogue in the folder's method (`area-<code>`), one for the board's own items when the plan's table of them has rows (`board-items`) and one for the comparison with the plan and the free pass (`plan-and-free-pass`); a method with no catalogue area, a plan whose table of the board's own items cannot be read and a folder that does not hold exactly one design are refused, naming what is missing. It declares which areas are coupled, power with mains and the manufacturing items with power, because one's verdicts depend on the other's findings, and the planner judges a coupled set in one group; a test fails when a declared coupling has no cross-reference in the catalogue, and a cross-reference alone is not a coupling. A narrow round's units are the groups its listed items fall in, and each unit's prompt names only its listed items; the comparison unit is a full round's. Every reviewer is granted `Read`, `Glob`, `Grep` and `WebFetch`, the retrieval grant a rule-kind item whose figure rests on a published document needs, and each session's start report is checked against the grant. The shared context holds what every unit needs and nothing of any one area: the extracts the folder command wrote, `round.json`, the check report, the views' and placement's index and measure records, the design folder's plan, rules, review record where it exists and every other `.md` and `.yaml` file, and every rendered view and the placement view as an image; never the circuit practice catalogue, the board's KiCad files or the designer's notes and session. A method that lacks one of the three sections the extract needs is refused, naming it, before any session starts, and so is a round file with a missing or malformed field. Each area unit's prompt carries the text of the catalogue section for its own area and says the other areas are not given; the board-items and comparison units carry no area section. Each group is judged by two replicas, the second asked for the failures first with the items and views the other way round, and the merge keeps any fail, and a round of three replicas has a third that runs on the small-tier model `claude-haiku-5-5` from a shared context of its own (the cache is not shared across models), whose fails the merge keeps like the others'. The merge gives every item a round judges exactly one verdict row, and refuses a verdict for an item the round does not judge and a `cannot judge`, naming the item and the view its Why asks for. It does not judge a rule-kind verdict or whether any verdict is right. It numbers this round's findings with the item units' in the checklist's order and the comparison unit's after, in its own order, and reports two findings that cite one view and board place (the first view name and the first `(x, y)` pair in What and where, compared as written) while keeping both. The merged round is written as `round-<n>.md` in the output folder, with the round heading, the opening fields, the Verdicts table, the Plan and free pass section and the Findings table or the line saying no finding was raised, in the order the method gives, to be appended below the record's earlier rounds and committed by whoever started the round, at the end of the round and before any change to the board. A vertical bar or a line break in a Verdicts or Findings cell does not refuse the merge: `round-<n>.md` writes each run of line breaks in such a cell as one space and each vertical bar as a slash with one space either side (`a | b` as `a / b`), while the command's own `record.json` keeps every cell as the reviewer wrote it. A resolved `cannot judge` is one row recording the `cannot judge`, the view or the document and the verdict reached, and the unit's prompt on the re-run names the document, to open with Read, and its source. The unit that raised a finding writes its Planning shortfall entry from the plan row; after the merge the designer names the item or step to amend and the commit. The caller's time budget is 350 seconds, so that the planner sizes groups well clear of the bound the proof holds the run to, and the most sessions at once is the caller's `bound`, 30, the largest number of reviewers at once the live runs ran with no call refused for a rate limit (20 forks at once in the design loop's run, 30 in the pre-order round's, every fork reading the shared context from the cache); it is a value to change when a run is refused, a plan with fewer forks than that runs them all at once, and the kit command's `--bound` overrides it. The proof's dry output prints the bound and this basis. It needs the agent command line on the search path and logged in, as the kit's command does, and no KiCad.

**The proof.** `task hw:review-proof -- --work <new folder outside the repository>` (`hardware/tools/layout_review_proof.py`) is one command. The work folder is laid out so that nothing a session must not read is in a folder above its working directory: the review folder is `<work>/review-tree/review` and `review-tree` holds nothing else, the seed list, the seeded copy and the kept work tree are under `<work>/seed/`, each round's output is under `<work>/out/<round>/`, and the record and its text are in `<work>` itself. The two rounds run one after the other on the same review folder, so a pre-order session starts where a design-loop session did; the design loop's output is outside `review-tree`, which a test holds, but the exposure the layout cannot remove remains: a session that guesses a path two levels up (`<work>`, and from it `out/` and `seed/`) can read it, the same exposure as the caveat under the review kit command. The design loop's two replicas (a full and a hunt framing) run on the small-tier model `claude-haiku-5-5`, because the design loop is run often and the small tier costs a fraction of the mid-tier for the same findings; the pre-order round's first two replicas run on the mid-tier `claude-sonnet-5-5` and its third on `claude-haiku-5-5`, with its own shared context counted as one more root. The cost model holds prices for each model and `--dry` predicts every session at its own model's prices, printing a `MODEL` line for each round that names how many forks run on which model. `--dry` also prints a `WARNING` line when the design loop's predicted cost or time is over its bound or within a tenth of it, since a live run is then likely to fail the bound or to need a second run. It runs `task hw:review-seed` with its `--keep-work-tree` flag, which keeps the seeded copy's git work tree and prints the commit that holds the design as the check judged it; writes the review folder with the folder command from that work tree and commit, layout facts and round file included (the method and this readme from this repository); loads the five recorded single-reviewer runs in `hardware/tools/tests/fixtures/review_baselines/layout_single_runs.json` as the baselines, refusing before any session starts when their seed list, design key (a hash of the files the layout review reads of the proof design, so a change to a file it does not read, such as the catalogue extract, leaves the recorded runs valid) or model is not this run's; runs the layout caller through the review kit's command on the agent command line with two replicas of each group on the small tier, the design loop's round, and again with three, the pre-order round's, every fork running together; and judges the design loop's run by the kit's pooled criterion with a cost multiple of 1.25. The baseline key holds the model the recorded single-reviewer runs ran on, `claude-sonnet-5-5`, and not the fanned-out run's, so a small-tier run is judged against the mid-tier baselines. The criterion holds when the seeds found are no fewer than the fewest any recorded single run found, no seed every recorded single run found is missed, the wall time is at most half the single mean and the cost at most 1.25 times its mean; a design-loop run within a tenth of a bound is followed by a second run in `out/design-loop-2`, and both are judged together, never a third, and the pre-order round's figures are recorded and not bounded. The single reviewer is never run again. It needs what `hw:review-seed` needs, the agent command line on the search path and logged in, and money: a shared context and a fork for each group and replica, for each of the two rounds (`--only design-loop` or `--only pre-order` runs one of them). `--dry` seeds the copy, writes the folder and prints each round's plan and its predicted cost and time beside the bounds, and starts no session. The record, `proof-record.json` and its text `proof-record.txt` in the work folder, gives every seed with the replicas that raised it, the findings that match no seed, the verdicts item by item with the differences from the single runs for an explanation, each session's wall time, tokens read from the cache, written and generated, cost and first-call cache read, the document retrievals and the ones that failed, counted from the saved streams since the kit's telemetry does not count them, and the calls refused for a rate limit, counted from the executor's retries. It decides nothing beyond the criterion: a seed not reported is closed where the gap lies and the proof repeated in a new session, and the layout caller's bound on groups at once is set from the record. `--design-model` (default `claude-haiku-5-5`) is the model the design loop's replicas run on and `--pre-order-model` (default `claude-sonnet-5-5`) the model of the pre-order round's first two replicas, the third staying on the small tier, `--bound` limits the sessions at once, `--json` prints the result as one JSON document, and the command exits 0 when the criterion holds, 1 when it refuses, a run fails or the criterion does not hold, and 2 when a tool or the agent command line is missing. The small-tier prices behind the predicted cost were fitted from one recorded small-tier run and checked against two later ones, within 15 per cent; a run with a different thinking volume is mispredicted.

## The critical-routing check by unit

The critical-routing check, step 4 of the method's [routing section](../docs/board-design-method.md#routing-critical-nets-by-hand-and-locked-then-the-rest), can be judged by unit: one reviewer for each set of coupled areas of the layout practice catalogue and one for the board's own items, each a fork of one shared context that [the review kit's command](#the-review-kit-command) builds from the review folder, two reviewers of each so that any fail stands, and the units merged with no model into one pass of the layout plan's `## Critical routing` section. It is the same check as the one reviewer's, carried out in parts, and judging it with one reviewer stays valid. The fanned-out form is relied on only once its proof is recorded; until then the method relies on the single-reviewer form. Two commands carry it, both on demand and in neither the build round nor the nightly ([When the board check runs](#when-the-board-check-runs)): the folder command that writes the review folder and the critical-routing caller that the review kit's command runs.

**The folder command.** `task hw:review-folder -- --review critical-routing --repo <repository> --commit <commit> --design <board folder from the repository's root> --out <new folder> --views <views folder> --number <n> --view-command <text>` (`hardware/tools/review_folder.py`; repeat `--view-command` for each command the views were rendered with; `--placement <placement folder>` when the placement view was rendered) writes the folder the check reads, outside the repository. It needs git and Python, no KiCad and no model. The pass's fields are the pass number, the commit judged (taken from `--commit`) and the views, and no more: the round file `round.json` holds no kind and no check lines, `--kind`, `--check-line`, `--item`, `--region`, `--others` and `--check-report` are refused, and `--round-fields` is left out or given as `number,commit,views`, the default, and no other set. The method extract `method-extract.md` holds the routing section as well as the layout review sections and the whole catalogue. The placement view is taken only when `--placement` is given, and the pre-order check's report not at all, since that check is not run at this step. A pass after the first copies no review record, the earlier passes being in the `layout-plan.md` the commit holds. A missing or malformed field, a views folder without an `index.txt`, a folder inside the repository and the other refusals of the layout mode refuse the command, naming the cause and writing nothing. The `--add-view` and `--add-document` modes serve this folder as they serve a layout review's, and the folder's checklist is the catalogue's items and the plan's board items, with no comparison with the plan. Without `--review`, or with `--review layout`, the command writes the layout review's folder as before.

**The critical-routing caller.** `hardware/tools/review_caller_critical_routing.py` is the caller `--caller critical_routing` names (`task hw:review-run -- --caller critical_routing --review <review folder> --out <output folder> --model claude-haiku-5-5`), run on a review folder the folder command wrote in this mode; a folder written for the layout review, whose round file has a kind and check lines, is refused. Its units are one for each area heading of the catalogue in the folder's method (`area-<code>`) and one for the board's own items when the plan's table of them has rows (`board-items`); there is no unit for a comparison with the plan or a free pass. The catalogue helpers it shares with the layout caller, the areas and items of a method section, the board's own items and the couplings, are in `hardware/tools/review_catalogue.py`, which both import; the couplings are the layout caller's, power with mains and the manufacturing items with power. A method with no catalogue area or without the routing section, a plan whose table of the board's own items cannot be read, a folder that does not hold exactly one design and a round file with a missing or malformed field are refused, naming what is missing, before any session starts. Every reviewer is granted `Read`, `Glob`, `Grep` and `WebFetch`, as the layout caller's are, and each session's start report is checked against the grant. The shared context holds the extracts, `round.json`, the views' index and records, the design folder's plan, rules and other `.md` and `.yaml` files, every rendered view as an image and the placement view when it was rendered. It is one stream message, and the review kit refuses a shared context over 268,435,456 characters (the agent command line's own limit, read from its refusal at version 2.1.304) before any session starts, naming the largest group of artefacts; a net's view holds only the tiles with some of the net's copper so that a board of full size stays under it.

Each reviewer decides which of the items of its unit bear on the critical nets and gives every item of its unit one verdict row: `pass`, `fail`, `not applicable` or `cannot judge` for an item that bears, and `bears on no critical net`, with the reason in Why, for one that does not. A fail raises a finding naming the item and what and where. The replicas are merged any-fail with `bears on no critical net` last of the verdicts, so an item one replica judged as bearing is judged. The merge gives every item of the checklist exactly one verdict row, and refuses an item with no row or two, a verdict for an item that is not on the checklist, a `cannot judge` still held (naming the item and the view its Why asks for), a fail with no finding, a finding of an item that does not fail, a fail that cites another item's finding, a finding with an empty what and where, a reason missing for an item that bears on no critical net and a pass in which no item bears on a critical net. It does not judge a rule-kind verdict or whether any verdict is right. The merged pass is written as `pass-<n>.md` in the output folder: for the first pass the section heading `## Critical routing` and `### Pass 1`, for a later one `### Pass <n>` alone; the **Board judged** and **Views** fields from the round file; the verdict table `| Item | Kind | Severity | Verdict | Rests on | Why |` with a row for every item that bears on the critical nets; and, below it, every other item on a line of its own, `` - `<item>`: <reason> ``. A fail is rendered as a plain `fail` whose Why holds the finding's what and where, for the designer to put right in the row before the router runs, as step 4 says, writing `fail, then <verdict> at <commit>` after judging that one item again with a single reviewer. The pass has no findings table and no round number. Whoever runs the check appends the file below the section's earlier passes, never in place of one, and commits it before the router runs; the pass number, the commit judged and the views are theirs to give. A `cannot judge` is resolved within the pass as the layout review resolves one, with the folder command's add-view and add-document modes and a re-run of the unit (`--rerun`), and the row is written `cannot judge, then <verdict>`; a `cannot judge` resolved to `bears on no critical net` is rendered as its list line, which has no verdict cell, with the prefix `Cannot judge: <why>` at the start of its Why. Both replicas run on the small-tier model `claude-haiku-5-5` (pass it as `--model`, so the review's own shared context is the replicas' and none is built for a model no replica uses), a full and a hunt framing; the time budget is 350 seconds and the most sessions at once is the caller's `bound`, 30, the layout caller's. It needs the agent command line on the search path and logged in, as the kit's command does, and no KiCad. The tests need no model and no KiCad.

**The proof.** `task hw:critical-routing-review-proof -- --work <new folder outside the repository> --seeded-repo <work tree> --seeds <seed list>` (`hardware/tools/critical_routing_review_proof.py`; `--kicad-cli`, `--resvg`, `--baseline-model`, `--design-model`, `--bound`, `--baselines` and `--dry`) proves the fanned-out form on one seeded copy of `hardware/proof/method-proof`, the only committed design whose layout plan holds a critical routing section. The one difference allowed is a reference appended to a region's parts, with no bound changed and no reference removed or moved between regions, and the plan in each commit just before the reference's footprint first appears on the board must list it, in a commit after the commit before the first placement, so a reference listed once, dropped, placed and listed again fails, as does one listed in the commit that places it or after, and the floorplan is read as the commit before the first copper holds it, so a reference appended only after that copper is not compared, while one appended before it and placed after it is still held to the plan in the commit before the one that places it;
- the placement section as it stood in the commit before the first track, or as the checked-out commit holds it while no commit carries copper: at least two `### Candidate <n>` subsections, each with a **Commit** in the history before the first track, holding the board, placing its parts differently from every other candidate's commit, judged by each part's reference, position, angle and side and not by the board file's bytes, so two files differing only in a text label or an identifier are one placement, and named by its **Renders**; its **Measures**, the `LENGTH`, `CROSSINGS` and `OUTSIDE` lines as `measures.txt` gives them, the same as the placement command's own measures of the candidate's commit, recomputed from that commit's board against the floorplan in the commit the section is judged in, with the references the plan appended removed where that commit's board does not hold them; its verdict table with one row for every placement item of the method and the board's own items in that commit, each `pass`, `fail` or `not applicable`, a `not applicable` only for an item the plan table marks `no`; a **Chosen** candidate that leaves no part outside its regions; and every footprint at the first track where the chosen candidate put it, by reference, position, angle and side;
- the critical routing section's `### Pass <n>` subsections, numbered from 1: each **Board judged** commit in the history, the first one's board holding at least one track, arc or via and all of them locked, a later one following the previous pass's router commit with no commit between adding or changing an unlocked track, arc or via, nor a merge bringing one in from another line of history; each pass's router commit, the first commit after its Board judged commit that adds or changes an unlocked track, arc or via, first appearing on one line of history and not in a merge commit, and the pass as it stood in the commit before that one, the same as now; every checklist item of that commit, or of the checked-out commit for a pass with no router commit, in the pass's verdict table or its list of items bearing on no critical net, `` - `<item>`: <reason> ``, exactly once; and each `fail` followed by `, then <verdict> at <commit>`, the commit after the Board judged commit and before the router's. Only the last pass may have no router commit; it is then judged as the checked-out commit holds it. With `--routed`, given once the router's commit is made, the last pass may have none either, and a board with no critical routing section fails, so locked or uncommitted router copper fails rather than reading as `router not yet run`.

Each check is one line, `CHECK | <check> | PASS | <detail>` or `CHECK | <check> | FAIL | <detail>`, one line for each thing a check finds wrong, and a `RESULT | PASS`, `RESULT | FAIL` or `RESULT | REFUSED` line comes last. The result line says `before first track` when no commit carries copper yet, a track, an arc, a via or a pour, and `router not yet run` when the last pass has no router commit. With `--json` the same checks and result are printed as one JSON document, with `result`, `detail`, `checks` (each with `check`, `verdict` and `detail`) and `refusals`. The method gives what each check's `FAIL` means at each step that runs it.

A commit a record cites that is not in the repository, or not in the checked-out commit's history, fails as not in it. So a branch whose board is judged this way merges without rewriting its history, by a merge commit, never squashed, rebased or force-pushed: the records cite its commits.

It refuses, judging nothing, with a `REFUSED` line naming the cause: a board that is not in a git work tree, or git older than it needs; a shallow clone, which lacks the commits the records cite; a board or `layout-plan.md` that git does not track or that differs from the checked-out commit; and a board that cannot be read. The exit status is 0 when every check passes, 1 when any fails, and 2 when the command is refused.

## The layout review record history

`task hw:review-history -- --folder <board folder>` judges the `layout-review.md` in the board's folder against the repository's history, as the completion checks of the [Layout review](../docs/board-design-method.md#layout-review) step's "Judge the record" list run it. It reads the record and the board's design files from git, as each commit holds them. It needs git and Python only, no KiCad. It writes nothing: what it reports can be judged again from the history at any time.

The board's design files are the files KiCad reads for it: everything tracked in the board's folder, the sheets its schematic reaches and the libraries its library tables name, less the folder's own records, its markdown and YAML files, the review record among them. So a record's own commits, and a finding's closure, never count as a design change, and nor does an edit to any other markdown or YAML record in the board's folder, the separation basis record among them: the closing-round check judges the files KiCad reads. The folder must track exactly one KiCad project.

It reads every version of the record reachable from the checked-out commit, and judges:

- the round structure: a round must be fully accounted for by the parts the command reads, in the record or any earlier version of it, or it fails, naming the board, the round and the line. A round heading that is not exactly `## Round <n>` (n a positive integer, no leading zero), a round given twice, or a code fence left open fails. A round runs from its heading to the next `## Round <n>`, and a line in a code fence neither ends it nor counts as a heading. Outside a code fence a round may hold no heading line (one beginning `#`, an HTML heading, or an underline of dashes or equals signs) but `### Verdicts`, `### Findings` and `### Plan and free pass`, each at most once. It must hold `### Verdicts`, a part of one table headed Item, Kind, Severity, Verdict, Rests on and Why. `### Findings` is one table with Finding, Raised by, Severity and What and where columns, each finding numbered once, or only the line `This round raises no finding.`, and may be left out of a round with no finding. Text, a second table or a code fence in either part beside its table fails. `### Plan and free pass` is prose that is not compared;
- the rounds kept: a `## Round <n>` heading in any earlier version of the record that the record now lacks fails, and so does a record holding no round;
- each round as first recorded: the round's end-of-round commit is the first commit, oldest first, whose record holds its heading. In that commit the round's opening lines, those up to its first subheading, its `### Verdicts` table, and its `### Findings` table's findings, none removed or added, each with its number, Raised by, Severity and What and where, must be as the record now gives them. The Closed by column is the one field that changes after a round is recorded, so it is never compared, and nor are the findings' other columns;
- each round's order: the round's end-of-round commit must be an ancestor of, and not, every commit after the round's Board judged commit that changes the board's design files;
- the closing round, the highest-numbered round now, judged on design files unchanged since its end-of-round commit;
- the round kind: a round states its kind in its opening lines as the bullet `- **Round kind**: full` or `- **Round kind**: narrow`, a narrow round being one a fresh reviewer limited to the items a fix touches. The closing round must state one, and a closing round that is narrow fails, since only a full round closes the review. An earlier round need state no kind, and is compared as first recorded like any other. A narrow round's `### Verdicts` table holds only the items it judges, and a closing round of kind full must hold a verdict for every item that round 1's table holds and for every item of each earlier full round (the `round completeness` check), so a narrow round labelled full does not close the review. A closing round stating its kind more than once, or in any other form than that bullet, is refused.

Each check is one line, `CHECK | <check> | PASS | <detail>` or `CHECK | <check> | FAIL | <detail>`, one line for each thing a check finds wrong, and a `RESULT | PASS`, `RESULT | FAIL` or `RESULT | REFUSED` line comes last. A failing line names the board's folder, the round and what differs. With `--json` the same checks and result are printed as one JSON document, with `board`, `result`, `detail`, `checks` (each with `check`, `verdict` and `detail`) and `refusals`.

A commit the record's rounds were first recorded in must be in the repository, so a branch whose record is judged this way merges without rewriting its history, by a merge commit, never squashed, rebased or force-pushed. It follows the record by its path, so a board folder moved with its history leaves the rounds recorded before the move unread; keep the folder where it is, or judge the record before the move. A board folder at the repository's root takes every tracked file there that is not a markdown or YAML record for a design file, the firmware's included, so give a board a folder of its own.

It refuses, judging nothing, with a `REFUSED` line naming the cause: a folder that is not in a git work tree, or git older than it needs; a shallow clone, which lacks the commits the rounds were first recorded in; a folder that does not track exactly one KiCad project; a record or design file that git does not track or that differs from the checked-out commit; and a closing round that states no round kind, states it more than once, or states one other than `full` or `narrow`. The exit status is 0 when every check passes, 1 when any fails, and 2 when the command is refused.

## What a design must satisfy

For each design the check runs KiCad's own electrical rule check on the schematic. It also runs KiCad's own layout rule check once, on a temporary copy, with schematic parity on and every zone refilled first. KiCad does the checking itself. A router's or editor's "no violations" is never accepted in its place. A design fails on any of these:

- **Any violation KiCad reports**: electrical, layout, unconnected item, or layout-schematic disagreement. Warnings count.
- **Any check set to ignore**, in the project's severities or in a custom rule's `(severity ignore)`. This applies even when ignore is KiCad's own default for that check, as it is for `missing_courtyard` and `footprint_filters_mismatch`. Set every check to error or warning.
- **Any violation marked as excluded**, whether in the project file's exclusion lists or by a custom rule's `(severity exclusion)`. Fix the violation instead.
- **A custom rules file KiCad declines to load.** KiCad drops a whole rules file it cannot parse, without saying so, and that would leave every custom rule unchecked. The check detects this and fails the design. It then names the first rule KiCad rejects, with its line, or a missing `(version 1)` header. When no one rule can be named it says why: the file is not well-formed at a given line, or every rule loads on its own and what KiCad rejects lies in the comments between them. It finds that rule by re-running KiCad's layout check on the file's rules a few at a time, so the editor is never needed to find it. The check knows the file loaded from a marker rule it appends, which fires on the items of the layout's net with the fewest items.
- **A layout check whose report was cut short.** KiCad reports at most 199 assertion failures and drops the rest at random. A run reaching that many therefore fails the design, saying the report was cut short, because a failure of the design's own assertion rules may be among those dropped.
- **A net KiCad named itself** (`tool_named_net`). KiCad gives a net nobody labelled a name beginning `Net-(`, such as `Net-(R3-Pad1)`, wherever it sits in a sheet path. The design fails, naming the net and the pins it joins, so a reader following the schematic by its nets is never left with a name that says nothing. Give the net a label that says what it carries. A pin nothing is connected to is exempt: KiCad names it `unconnected-(…)` and it carries no net.
- **A hierarchical sheet with no name of its own** (`unnamed_sheet`). A sheet whose `Sheetname` is blank or missing, or is KiCad's default, `Untitled Sheet`, optionally followed by a number when a second is left unnamed, fails, naming the schematic that draws it. Name the sheet for what it does. The root sheet has no sheet symbol and is exempt. Whether a sheet's arrangement is readable is not decided here; the schematic review judges it.
- **A custom rule whose name contains `pre-order check`.** Those words are reserved for the rules the check adds to the copy it checks. The rules the check recognises in KiCad's report are named afresh for every run, so no design rule can pass for one of them.
- **No mains declaration.** The project text variable `MAINS` must be `present` or `none`. A design that declares `present` must have a net in the `Mains` net class on its layout, since that is where the separation rule is enforced. A design that declares `none` may have none there.
- **Any disagreement about which nets are in `Mains`.** Three things say which nets are in the class, and each is read as KiCad itself resolves it: the layout (KiCad's answer for the layout's nets with the layout's project file and its own net classes, read as [the class read](#how-a-class-is-read) reads them), the schematic (KiCad's own netlist of it, which carries its net class directives), and the project file's net settings (its assignments by name and its patterns, which KiCad resolves for every net the layout, the schematic or an assignment names, copper or not). Every net must be in the class in all three or in none. A net in only some of them fails by name, saying which have it and which lack it. The usual fix is to save the schematic, so the project file carries its assignments, and update the layout from the schematic. A class only the layout gives a net comes from a `(net_class ...)` block that older KiCad versions wrote into the layout file, which KiCad 10 still honours.

- **Workmanship that breaks a rule of the method's workmanship area** (`WORK-` items of the layout practice catalogue in [`docs/board-design-method.md`](../docs/board-design-method.md#workmanship-work)). KiCad measures four of them: the angle at a joint between two tracks, the length of a straight run, a track end left unconnected, and a via left unconnected. The design's rules file must hold a `track_angle` rule and a `track_segment_length` rule, each with no condition or the one condition `A.Type == 'Track'` and no layer, so they hold on every track; a rules file lacking either, or holding it narrowed, fails as `workmanship_rule`. So does any other rule holding either constraint, before or after the one in force, conditioned or not, whose minimum is looser than that rule's or not written in the same form: in KiCad the last matching rule wins, so a later rule at a lower figure for some tracks would loosen the item there while KiCad's check passed. The violation names the rule, its line in the rules file, and both figures. KiCad reports a via unconnected or connected on one layer only, and a track end left unconnected, unaided. KiCad compares every two tracks meeting on one layer anywhere but at a pad, a branch included, so a route branches at a pad. What KiCad does not measure the check measures itself from the layout file. Wherever a measure asks whether a track meets a pad, it judges that from the copper, as KiCad's connectivity joins them: KiCad joins a track to a pad wherever the track's copper reaches the pad's. A track's end is a round cap of half its width, and the track meets a pad at an end where that cap reaches the pad's copper; a track whose copper runs over a pad with neither end reaching it, through the pad's centre or off it, crosses the pad. A test holds this reading to the installed KiCad's own connectivity. It sizes a pad's copper when the pad is a circle, an oval, a rectangle or a rounded rectangle; a pad of any other copper on a layer where tracks of its net run fails as `workmanship_pad_copper`, naming the pad, rather than being guessed. Two tracks of a net meeting on one layer at a pad are a route turning through it, and the check holds the angle between the ways they leave it to the `track_angle` rule's own minimum, read from the rules file (the last rule in force, as KiCad applies it), and states that figure in its report (`workmanship_pad_corner`). Every other measure is held to a figure the design sets as a project text variable, a plain decimal number:

  | Variable | Item | What the check measures |
  |---|---|---|
  | `WORK_DETOUR_RATIO` | `WORK-2` | Each net with tracks and two or more pads: the length of all its tracks and arcs, against this many times the minimum spanning tree, in straight lines, of the centres of all its pads. Zones never enter the measure, so a zone can neither exempt a net nor take a pad out of the tree (`workmanship_detour`) |
  | `WORK_PAD_ANGLE_DEG` | `WORK-4` | Each pad where three or more tracks of a net leave it on one layer, a branch, which KiCad's corner rule does not compare: the angle between each two of the ways they leave it, against this many degrees at least (`workmanship_pad_corner`) |
  | `WORK_NECK_MM` | `WORK-8` | Each run of track narrower than its net class's track width (from the project file, the class KiCad ranks first for a net in several): passes only when it reaches a pad of its net and runs no more than this many mm off its net's pads' copper; a track wider than its class's width never fails (`workmanship_width`) |
  | `WORK_ANGLE_TOLERANCE_DEG` | `WORK-9`, `WORK-10` | Each straight track's direction, and each arc's at both its ends, against a multiple of 45 degrees from the board's edges (`workmanship_direction`). The edges' direction is that of the longest straight side of the outline as drawn: a line, a rectangle's four sides less their corner rounding, a polygon's straight runs, and those shapes in a footprint where it places them; arcs, circles and curves give none, and an outline with no straight side is held to the board's own axes. Also the angle at which a track enters a long pad, against the pad's long axis |
  | `WORK_PAD_ENTRY_RATIO` | `WORK-10` | Each track meeting, at one end and not the other, a pad more than this many times as long as it is wide, or whose copper runs over such a pad with neither end meeting it: its direction there, against the pad's long axis (`workmanship_pad_entry`) |
  | `BARRIER_COPPER_MM2` | `MAINS-5` | Each part with pads on a `Mains`-class net and on another net: the strip between the two groups of pads, where their boxes lie apart along one axis, and the area of every track, via, pad and filled pour of the board that lies in it, on each copper layer, against this many mm² at most (`mains_barrier`). The check measures the pours as KiCad has just refilled them. A pad on a `Mains`-class net is a `Mains`-class pad whatever its number, copper layer or net name. A pad that carries no net is in neither group: one on a net named `unconnected-(...)` that no other pad of the board carries (KiCad's name for a pin flagged no-connect), and one with no net that has no number or no copper layer. A net of that name carried by two or more pads is a real net. A part whose pads off the class are all such pads is not judged; the accepted limit is that a netless pad with no number but with copper, such as a floating tab, is exempt too. The copper of every pad, those included, is still added up in the strip |
  | `PASTE_OVER_VIA_MM2` | `MFG-4` | Each via's hole and each paste opening, a pad's shape grown by its paste margin and ratio, the pad's own, its footprint's or the board's: the area of the hole under the opening, on either side of the board, against this many mm² at most (`paste_via`) |
  | `TEST_COURTYARD_MM` | `TEST-5` | Each test point, a part whose reference designator begins `TP`: the distance from the copper of its pad to the courtyard of every other footprint, on the front and on the back, taken as the box about the part's drawing on that side's courtyard layer, against this many mm at least; a part with no courtyard on a side is skipped for it (`test_point_courtyard`) |

  A variable that is missing, or not a plain decimal number within its range, fails as `workmanship_figure`, naming it. The report states, under each design's verdict line, the figure it read for each measured rule.

  A third measured rule has its figure in the board's own settings: `MFG-6` holds every pour, as KiCad has just refilled it, to the board's minimum clearance (`board.design_settings.rules.min_clearance`, the `Minimum clearance` row of the rules table): the gap from a zone's fill to each track, via and pad of the zone's net on a layer that the fill stops short of, without touching it, is no narrower than that figure (`pour_gap`). KiCad's layout rule check does not compare copper of one net, so a slot between a pour and its own net's track is its blind spot. A board stating no minimum clearance fails as `pour_gap`, naming the setting. The report's `FIGURE` line for it names the setting and the figure read.

  Three more measured rules need no project text variable of their own, because the proof designs carry none for them; each figure is an inherent zero, and the report's `FIGURE` line for each says so. Two further rules, below them, are counted or judged from the design's files alone:

  - `DECOUPLE-6` ("No via sits between a decoupling capacitor's supply pad and the pin it decouples", `decoupling_via`). Its figure is an inherent zero: no via in the decoupling path. The circuits and their decoupling parts are the layout review views' own (`board_views.circuits`): a circuit is a footprint whose reference begins with `U`, with supply nets the nets of its pads whose `pintype` in the layout file is `power_in` or `power_out`; a decoupling part is a two-pad part that is not itself such a circuit, with its pads on two different nets that are both of one circuit's supply nets, kept with the nearest such circuit. For each, the supply pad is the part's pad not on a net of a ground net class (both pads when neither is, or both are), and the pin it decouples is the circuit's pad on the same net nearest it. A via on that net whose centre lies inside the box about the two pads' copper, or whose copper reaches into it, is a violation. A via of another net in the box is not in the capacitor's path and is not one. A board whose pads carry no `pintype` has no decoupling parts and passes; the report's second line for the item, `DECOUPLE-6 decoupling paths measured`, read from `the layout's pad pin types`, states how many paths of how many circuits with a supply pin were measured, so a pass that measured nothing shows as `0 paths of 0 circuits with a supply pin`. A design not marked `NOT_FOR_MANUFACTURE=true` whose integrated circuit has netted pads and none with a `pintype` of `power_in` or `power_out` fails as `decoupling_pintype`, naming the part, since the rule would find no supply nets for it and measure nothing; a circuit none of whose pads is on a net is not refused. An integrated circuit is skipped only when the catalogue number of its position (the `LCSC` field, the number the parts check compares) maps to an entry of the catalogue extract whose optional `category`, the first category name of the part's parts-library record, is exactly one of the two strings of the closed list in [The no-supply categories](#the-no-supply-categories); a skipped part with a pad typed `power_in` or `power_out` still fails, the layout contradicting the category. Every other case is refused: an extract that cannot be read or is unusable (one marked synthetic on an orderable design included), a number that is `none` or absent from the extract, an entry without a `category`, and a category outside the list. A design marked not for manufacture is not refused on this, because the gate's proof design is such a board, and the coverage line shows what was measured.
  - `MFG-7` ("Every part's reference designator is on a silkscreen layer", `reference_off_silkscreen`). Its figure is an inherent zero: no reference off the silkscreen. A footprint's `Reference` text must be on `F.SilkS` for a part on the front and `B.SilkS` for a part on the back, and shown; a reference on any other layer or the other side's silkscreen, or hidden, is a violation naming the part, and so is a footprint with no `Reference` text at all, named by its library entry. A footprint left out of the bill of materials (`exclude_from_bom`), such as a mounting hole, may hide its reference on the right silkscreen; a hidden reference is one written `hide` or `(hide yes)`, on the text or inside its `effects`.
  - `MFG-9` ("Each designator stands outside every part's body, beside its own part", `designator_astray`). Its figure is an inherent zero: no designator astray. A designator's text box is estimated from the footprint's text size and thickness and the character count of the name (0.6 of the width size per character, widened by the thickness) and placed as the footprint is placed; a part's courtyard is the box about its drawing on the courtyard layer of the text's side. A box reaching more than 0.05 mm into any part's courtyard, its own included, is a violation naming the part, and so is a box nearer another part's courtyard than its own part's by more than 0.1 mm. A part that draws no courtyard of its own is held only to the first of these, since a missing courtyard is a different defect and leaves no gap to compare.
  - `MFG-10` ("Each side with assembled surface-mount parts carries three fiducials", `side_fiducials`). Its figure is the item's own count, three fiducials, which is no project text variable; the report's `FIGURE` line says so. A fiducial is a pad carrying KiCad's global fiducial pad property (`pad_prop_fiducial_glob`), counted on the side its footprint sits on. A side carries surface-mount parts when it holds a footprint with the surface-mount attribute that is not itself a fiducial and is not left out of the position file (`exclude_from_pos_files`), so a test point the assembler does not place does not make a side count. Each such side with fewer than three fiducials is a violation naming the side with the count of parts and fiducials found. A design with no surface-mount part is not failed. A fiducial's size and keep-out are not judged.
  - The polarity mark (`polarity_mark`) has no figure and no `FIGURE` line. A part is polarised when its schematic pins are named for anode and cathode (`A` and `K`, or the words) or plus and minus, when its schematic symbol is a library item whose name begins `C_Polarized`, or when it has three or more pads on distinct nets; a footprint whose pads are all on one net or are all non-plated holes, a mounting hole, is left out, and a plated through-hole pad makes a footprint a candidate as a surface-mount pad does. Its first pin is the pad numbered 1. The pin is marked when a line, arc, circle, polygon or rectangle of the footprint on the silkscreen layer of the part's own side has its nearest point nearer the copper of pad 1 than to the copper of every other pad by more than 0.05 mm, and the footprint's silkscreen graphics taken together are not unchanged, to within 0.05 mm, by any turn or reflection that maps its pads onto themselves in position, size and shape while moving pad 1. Text, the designator included, is no mark. A polarised part that fails is a violation naming the part and its pad 1. A polarised part with no pad numbered 1 needs no first pin, and no mark, only when every plated pad is through-hole, its plated holes lie at two or more positions more than 0.01 mm apart, at least one of its plated pads is named, and no turn about the centre of its plated holes other than the identity maps the holes onto themselves in position and drill (an oval drill's long axis included); a hole is the pad's own `at` point with no drill offset, and the size and shape of the copper are not compared, so two holes of one drill under one rect and one round pad fit either way and are not excused, while two drill diameters key the part. Reflections do not count, since a placed part cannot be mirrored. Otherwise the part is a violation naming the part, with the text `has no pad numbered 1` and one reason: `its pads are surface-mount`, `none of its pads is named`, `its holes fix no orientation` or `its holes map onto themselves when turned`. A part with a pad numbered 1 is judged on that pad as before. The rule reads the schematic's netlist, KiCad's own export, for symbols and pin names, and the layout for pads and graphics.

- **A connection that departs from its pin allocation record** (`connectivity`, and `pin_allocation` for the record itself). Every design, mains or not, is held to a **pin allocation record**, the `pin-allocation.yaml` in the nearest folder at or above the design, found as the separation basis record is. It lists the board's channels under the key `channels`, and each entry has these keys:
  - `channel`: the channel's name, as the channel enumeration names it;
  - `net`: the schematic net that carries it, written as the schematic writes it. A net on the top sheet may be written with or without the leading slash KiCad puts before it, and a net on a sub-sheet is written with its sheet path;
  - `controller_pin`: the controller's own pin name, port letter then number, as in `PC6`. The check reads it off the controller symbol's pin name; a pin named for more than one function, such as `AREF/PB0`, answers to each of them. An entry that carries `rail` or `far_channel` (below) carries none;
  - `connector` and `connector_pin`: the connector's reference designator and its pin number, as in `J2` and `1`. A channel that stays on the board with no connector leaves out both, and is then held to its controller pin only. Giving one without the other fails the record. An entry that carries `rail` or `far_channel` always gives both;
  - `rail`: the name of the supply or return the connector pin carries, in place of `controller_pin`. A rail entry may stand in the record of a design that places a controller, so a connector's supply and return pins can be listed. Its `channel` is a label, unique within the record and not a name from the channel enumeration. Rail entries are exempt from the rule that a net is listed once, so a header with several supply or several return pins is listed in full; each connector pin is still listed once. A rail entry's net is held to its connector pin as any channel's is, and its name is compared with nothing;
  - `far_channel`, on a record whose top level carries `controller: none`: the name, as the channel enumeration names it, of a channel that another design in the same machine folder lists with a controller pin and a connector.

  A record whose top level carries `controller: none` declares that its design places no controller, as the heater wall board does. Each of its entries then gives `channel`, `net`, `connector` and `connector_pin` and exactly one of `far_channel` and `rail`, and carries no `controller_pin`. The declaration is accepted only for a design that places no part with a port-named pin and no part whose `LCSC` field equals the `lcsc` of the machine's controller part record; one that places either fails as `controller_part`, naming the part, and where the machine folder holds no controller part record the design is held to the port-named pins alone. A record that does not declare it must list at least one channel with a controller pin, so a design that places no controller and carries no declaration fails as before. Each `far_channel` must be a channel that another design's record in the same machine folder lists with a controller pin and a connector, and one that no such record lists fails the design, naming the channel (`pin_allocation`); a design with no machine folder, a proof design among them, is exempt from that comparison, as a synthetic controller already exempts it from the controller part rule. Another design's record is the one a different design in the machine folder is held to, found as its own folder finds it. The check does not compare the cable between two headers pin for pin; it holds that each far channel exists and is driven by the other board. The firmware tier's pin and sensor checks read only the controller's record and are unchanged.

  An entry may also carry `firmware_channel` or `firmware_sensor`; the firmware tier's checks read those, and this check ignores them and every other key it does not name. The record fails the design if it is missing, cannot be parsed, has no `channels` list, lists no channel, or has an entry lacking `channel`, `net` or, outside a rail entry and a record that declares no controller, `controller_pin`, or holding a blank or non-text value, or has a `controller` other than `none`; or if it lists a channel, a net (rail entries aside), a controller pin or a connector pin twice. A record marked `synthetic: true` passes only a design whose project text variable `NOT_FOR_MANUFACTURE` is `true`. Unlike the separation basis record it needs no signature and need not be committed to be read, though git still has to track it for the build round to see a change to it. The check asks KiCad for the schematic's netlist and then fails:
  - a channel whose net does not reach its `controller_pin`, or does not reach its `connector_pin` on its `connector`, naming the channel, the net, the pin the record names and the pin the net reached;
  - a channel whose net the design does not have;
  - any net on a controller pin the record does not list: a pin whose name is a port pin on a part the record names no connector for;
  - any net on a pin of a connector the record names that the record does not list for that connector. A connector the record names no channel for is not examined, and a pin nothing is connected to, which KiCad names `unconnected-…`, carries no net. An entry with no controller pin is held to its connector pin alone.

- **A controller that departs from its controller part record** (`controller_record` for the record itself, `controller_part` for the design). A controller is every placed part with a pin named as a port pin, the test the connectivity check applies. A design that places none is not held to the record. A design that places one is held to a **controller part record**, the `controller-part.yaml` that names the selected part. The record that names it is the one in the machine's own folder, `hardware/<machine>/`, the first folder below `hardware/` that holds the design (`hardware/proof/` holds proof designs and is no machine's, and a design directly under `hardware/` or outside it has no machine folder). It is found as the separation basis record is, nearest at or above the design, but a record not marked `synthetic` that sits anywhere else fails the design that finds it, naming the record, so a board's own folder cannot hold a design to a different controller. A record marked `synthetic` may sit nearer to a design than the machine's, in a proof design's folder, and satisfies only a design marked not for manufacture. Such a design is by definition not orderable, so a real board's draft marked so is not held to the machine's record. Its keys are `part` (the maker's part number), `lcsc` (the catalogue number) and `pins` (the port pins the part has, each written as `PC6` is), and `synthetic` when present. The check fails:
  - a design that places a controller where no folder at or above it holds the record, naming the parts it places with port pins (`controller_record`);
  - a record not marked `synthetic` that is not in the machine's own folder, naming the record (`controller_record`);
  - a placed controller whose `LCSC` field is not the record's `lcsc`, or that has none, naming the part and both numbers (`controller_part`);
  - a channel of the pin allocation record whose `controller_pin` is not among the record's `pins`, naming the channel and the part (`controller_part`).

  The rule identifies a controller only by its port-named pins, so a symbol with no port-named pin (pins named `GPIO4` or `P0.04`, say) is not a controller to it. The pin allocation rule catches that for a design that does not declare `controller: none`: it must carry a pin allocation record listing a channel with a port-named controller pin on its net, so a design whose only microcontroller has no port-named pin fails there. A design that declares `controller: none` is held by the controller part rule to placing no part with a port-named pin and no part carrying the controller part record's catalogue number. The residual the declaration leaves is a different microcontroller that has no port-named pin and another catalogue number, placed on a board that declares `controller: none`: neither rule can see it. The two rules together, with the declaration, are the guard. A library symbol that names a pin with the datasheet's suffix (for example `PC14-OSC32_IN` or `PH0-OSC_IN`) is split on `/` only, so such a name does not match the port-pin test; name the pin `PC14` or `PC14/OSC32_IN` so the controller is recognised.

A design that declares `MAINS` as `present` must also:

- assign every mains-referenced net to the net class `Mains`;
- state its separation in its own custom rules file (`<design>.kicad_dru`) as **one** rule, with no `(layer ...)` and one condition written exactly `A.hasNetclass('Mains') && !B.hasNetclass('Mains')`. The rule holds both a `clearance` and a `creepage` constraint, each written `(min <n>mm)` and no less than the signed record's figures;
- declare, through the project text variable `MAINS_ENTRY` set to `present` or `none` (an unset or other value fails, naming the variable), whether it carries nets ahead of the entry fuse. A design that declares `present` assigns each such net to the net class `Mains_Entry` as well as to `Mains`, and fails with no net in `Mains_Entry` or a `Mains_Entry` net outside `Mains`; a design that declares `none` has no net in `Mains_Entry`, and fails with one. A design that declares `MAINS` as `none` needs no `MAINS_ENTRY`. A fixture, a design marked `NOT_FOR_MANUFACTURE=true` and held by a record marked `synthetic: true`, is out of scope of the `mains_to_mains` requirement: it passes without the mapping and, when it carries none, without `MAINS_ENTRY`, and a mapping it carries is read in full and then held to `MAINS_ENTRY`. An orderable design, and one marked not for manufacture but held by a record not marked `synthetic`, is held to both.
- be held to a signed **separation basis record**. This is the `separation-basis.yaml` in the nearest folder at or above the design. Its keys are `standard`, `supply`, `working_voltage`, `pollution_degree`, `material_group`, `environment`, `barriers`, `mains_to_low_voltage` (a mapping holding `clearance_mm` and `creepage_mm`), `mains_to_mains` (a mapping, below), `accepted_by`, `accepted_on` and `synthetic`, and the inputs its figures are read at, each optional on a record unless the design declares `MAINS` present, which requires `overvoltage_category`, `altitude_m` and `barrier_types` (an explicit `barrier_types: []` is a stated none): `overvoltage_category` (a whole number from 1 to 4), `altitude_m` (a positive number of metres), `barrier_types` and `table_rows`. `barrier_types` is a list with one entry for each barrier named under `barriers` and no other, each entry holding `barrier` (the name used under `barriers`), `insulation` (`basic` or `reinforced`), `earth_bonded` (true or false, whether the low-voltage side of that barrier is bonded to protective earth), `touchable` (the low-voltage parts a person can touch beyond it, a list, empty where none) and `formed_by` (the part or spacing that forms it). `table_rows` is a list of the rows of the cited standard's or derivation's tables actually used for the design's inputs, never a whole table (the machine's record also carries eight functional **band rows**, insulation `functional`, location `conductor`, at its pollution degree and material group, holding a `creepage_mm` and a `clearance_mm` for working voltages from 10 V to 320 V, the table a listed pair's creepage at a working voltage below the supply's is read from; between two adjacent rows the figure is the linear interpolation rounded up to 0.1 mm, below the lowest row that row is read, above the highest there is no band figure, and a pair at the supply voltage keeps the signed mains-to-mains creepage; they enter no floor of a `mains_to_mains` figure, because the record holds no `downstream_basis`), each holding `citation` (a mapping of `document`, `edition` and `locator`, the table and row or the clause), `inputs` (a non-empty mapping of the input values the row is read at, drawn from `working_voltage_v`, `insulation` (`basic`, `reinforced` or `functional`), `overvoltage_category`, `pollution_degree`, `material_group`, `altitude_m` and `location` (`terminal` for a row that applies to the terminals of a part, `conductor` for one that applies to conductors elsewhere, which a row stating no `location` is)) and `figure` (a mapping of `clearance_mm` and `creepage_mm`, each a positive number of millimetres, at least one present). The check reads these keys for their form, and the separation floor rule below compares the signed figures with the floor the rows give. It refuses any key inside them, at any depth, that this list does not name, naming the key. The check compares `mains_to_low_voltage.clearance_mm` and `.creepage_mm`, in millimetres, and the figures of `mains_to_mains`. A record held by a design that declares `MAINS` present must carry `mains_to_mains`, the distances between conductors at different potentials of the mains supply: `clearance_mm`, `terminal_clearance_mm` (the clearance between the terminals of a part, no less than `clearance_mm`), `creepage_mm` (the creepage downstream of the entry fuse), `creepage_ahead_of_fuse_mm` (the creepage between conductors that only the supply's own protection clears a fault between, the basic-insulation figure, no less than `creepage_mm`), `entry_fuse` (the reference designator of the entry fuse, which must be a reference of the layout, and where `MAINS_ENTRY` is `present` one with a pad on a `Mains_Entry` net and a pad on a `Mains` net outside that class) and `held_at_reinforced` (a list, empty where none, of pairs of net names across a device whose bypass would defeat a safety function, such as the open contact of the interlock relay; each pair is held to the larger of each `mains_to_low_voltage` figure and the matching `mains_to_mains` figure, and each net must be in the `Mains` class), each figure a positive number of millimetres. `creepage_mm` may be below `creepage_ahead_of_fuse_mm` only when the mapping also holds `downstream_basis`, a statement of the prospective fault current at the downstream conductors and of the entry fuse clearing a tracking fault between them at that current within the time the standard allows, which signing the record accepts; without it the basic figure applies downstream as well. A record without the mapping, or lacking a key of it other than `downstream_basis`, fails like a missing figure, naming the key, and so does a key inside it that is not named here. A design that declares `MAINS` as `none` is exempt and needs no `mains_to_mains`. `accepted_exceptions` is an optional list, and an explicit empty list is the state of a record that accepts none; it holds the spacing shortfalls the record's owner accepts, each entry holding `pair` (`mains_to_low_voltage` or `mains_to_mains`), `constraint` (`clearance` or `creepage`), `between` (a list of two items, each a pad written as a reference designator, a dot and the pad name, as `J1.2`, or a net name, the one pair of items the entry excuses), `accepted_mm` (a positive number of millimetres, the least distance accepted, which must be below the figure of the rule that reports the shortfall), `reason` (the owner's ground), `bounded_by` (the independent element that bounds the fault the shortfall could cause) and `accepted_by` and `accepted_on` (who accepted that entry and when, under the same rule that signs the record). The check refuses an entry that is not a mapping, lacks one of those keys, holds another key, gives a key twice, names a `pair` outside `mains_to_low_voltage`, `mains_to_mains` and `same_connector_pins` or a `constraint` outside `clearance` and `creepage` (for the two spacing pairs), has a `between` that is not a list of two non-empty items or an `accepted_mm` that is not a positive number, as `separation_basis`, naming the entry's position and the key; a `same_connector_pins` entry is a third form, for the plated-hole spacing a connector's own pin pitch forces: it holds `pair` (`same_connector_pins`), `constraint` (`hole_to_hole`), `connector` (the reference designator of one connector, letters then digits, as `J630`), `pitch_mm` (that connector's pin pitch, a positive number of millimetres), `accepted_mm` (a positive number of millimetres, the least edge-to-edge distance between two of its holes accepted, which must be below the distance the board's plated-hole spacing rule holds), `reason`, `bounded_by`, `accepted_by` and `accepted_on`, and holds no `between`. Its ground, that the connector carries slow signals only and no fast signal crosses its strip, is the owner's assertion, which the check does not test. The check refuses such an entry that lacks one of those keys, holds a `between` or any other key, has a `constraint` other than `hole_to_hole`, a `connector` that is not a reference designator, or a `pitch_mm` or `accepted_mm` that is not a positive number, and a second entry naming a connector an earlier one names, as `separation_basis`, naming the entry's position and the key. A `nets_a` entry is a fourth form, for a mains-to-mains shortfall between two sets of nets (a divider chain, a neutral-referenced group, a pair of mains nets with copper of every kind between them): the key `nets_a` selects it, and it holds `pair` (`mains_to_mains` only), `constraint` (`creepage` or `clearance`), `nets_a` (a non-empty list of net names), `nets_b` (an optional non-empty list of net names; omitted, or equal to `nets_a`, the entry covers every pair of different nets inside `nets_a`), `working_voltage_v` (a positive number, the largest rms voltage across a gap between a net of one list and a net of the other at the top of the declared supply span), `accepted_mm` (a positive number of millimetres, the least distance accepted), `reason`, `bounded_by`, `accepted_by` and `accepted_on`, and holds no `between`. The working voltage is the owner's assertion, with its derivation (each net's fraction of the line voltage, or its stated offset from neutral) in `reason`; the check does not recompute it. The check refuses such an entry that lacks one of those keys (`nets_b` aside), holds a `between` or any other key, gives a key twice, has an empty `nets_a` or `nets_b`, a list that repeats a net or holds an item that is not text, a `pair` other than `mains_to_mains`, a `constraint` outside `clearance` and `creepage`, or a `working_voltage_v` or `accepted_mm` that is not a positive number, as `separation_basis`, naming the entry's position and the key. How the entries are judged against the layout is under `spacing_exception` below. `accepted_by` names the acceptor by the identity they record acts under in this project's requirement graph. The record fails the design if it is missing or cannot be parsed, or if a figure is missing or not a positive number. It also fails if it is unsigned: an `accepted_by` that is missing or a placeholder (`unsigned`, `tbd`, `todo`, `none`, `placeholder`, or anything in angle brackets), or an `accepted_on` that is missing, is not a `YYYY-MM-DD` date, or is later than today. A record marked `synthetic` passes only a design whose project text variable `NOT_FOR_MANUFACTURE` is `true`. The commit that adds or changes the record is its audit trail. A record that is untracked, ignored by git, staged but never committed, edited since its last commit, or deleted from the working tree therefore fails the design. A nearer uncommitted record is never passed over for a committed one further up. The record's own `accepted_by` and `accepted_on` are its single acceptance and cover the whole record, the exceptions included, so an entry dated after the record's acceptance fails and adding or changing an exception needs a fresh acceptance of the record.

The **separation floor** (`separation_floor`) compares the signed `mains_to_low_voltage` figures with the floor the record's own `table_rows` give, so a signed figure cannot sit below what its own inputs require. A row applies when its `working_voltage_v` and `altitude_m` are at or above the record's, its `overvoltage_category`, `pollution_degree` and `material_group` equal the record's, and its `insulation` equals the strongest `insulation` among `barrier_types`. An input a row omits does not constrain whether it applies; a row stating an input the record does not state does not apply; and where `barrier_types` is an explicit empty list, a row that states an `insulation` does not apply and a row that omits it does. `working_voltage_v` is compared with the number the record's `working_voltage` begins with, in volts rms. A `working_voltage` stating several figures, such as `50 V dc, 250 V rms`, is therefore read at its first, 50. The floor for each figure is the largest `clearance_mm` or `creepage_mm` over the applicable rows that give it, so a row giving only one figure counts for that figure only. The design fails where a signed figure is below its floor, where no applicable row gives a figure at all, and where the record lacks `overvoltage_category`, `altitude_m` or `barrier_types`, or a `working_voltage` that begins with a number. The failure names the record, the figure or key, the floor and the rows that give it.

The same floor is read for the signed `mains_to_mains` figures, from the rows whose `location` is `conductor` unless stated and that state their `insulation`: `clearance_mm` against the largest `clearance_mm` of the applicable rows of `basic` insulation; `terminal_clearance_mm` against the largest `clearance_mm` of the applicable rows of `basic` insulation and `location` `terminal`; `creepage_ahead_of_fuse_mm` against the largest `creepage_mm` of the applicable rows of `basic` insulation; and `creepage_mm` against the same rows, or, where the mapping holds `downstream_basis`, against the applicable rows of `functional` insulation. Where the working voltage lies between two rows of a creepage table, the record carries one derived row at the working voltage, its figure the linear interpolation between the two rows rounded up to 0.1 mm and its citation naming both rows and the interpolation; that row applies like any other, and is read as the floor in place of the higher row it was interpolated toward, which is not read for that figure once a row of the same `insulation` and `location` stands at the working voltage itself. A design that declares mains present with no applicable row for one of these figures fails, naming it, as does a `creepage_mm` below `creepage_ahead_of_fuse_mm` with no `downstream_basis`. The floor of the `mains_to_low_voltage` figures reads as before.

The **mounting holes** (`mounting_hole`) are held to the larger of the signed clearance and the signed creepage, on every layer, whether or not the fixing is bonded to protective earth. A mounting hole is a footprint whose pads are all drilled holes (a `thru_hole` or `np_thru_hole` pad with a drill) and which has at least one of four marks: every pad is non-plated; it carries KiCad's `exclude_from_bom` attribute, as its stock mounting-hole footprints do; its library item name (the footprint name after any `Library:` prefix) begins with `MountingHole`; or it has exactly one pad. The last two exist so that a custom plated mounting pad whose bill-of-materials flag was forgotten is not silently left out of the extent checks. They also take in a one-pin through-hole part, such as a test point, on purpose: it is held to the larger of the signed clearance and creepage, at most 1 mm over the signed rule. A footprint with a surface-mount pad, or a plated through-hole part of two or more pads that is in the bill of materials and not named for a mounting hole, such as a connector or a resistor, is a part and not a hole. Every non-plated hole, in any footprint, is held as well. The check measures from the layout file, as KiCad has refilled it, the distance from each mounting-hole footprint's pad copper and its courtyard to every pad, track, via and pour fill of a `Mains`-class net on every copper layer, and fails the design where one is nearer than that distance; a gap of exactly that distance passes. A footprint that draws no courtyard is measured by its pad copper alone. The copper of a net the fixing's own pads are on is the fixing's own: a hole's pad on a `Mains` net, and the copper of that net, are not measured against it, while its courtyard is still measured against every other `Mains` net's copper. After the signed rule, in a second KiCad run on the temporary copy, the check also appends rules holding each non-plated hole and the pad it is drilled through (so a pad larger than its hole is held at its pad's edge, in a part as well as in a hole footprint), and each plated hole on a net outside `Mains`, to that distance from every `Mains`-class item, with a probe for each kind of pad the layout has that must fire for the rules' pad-type conditions to be known to match. The failure names the design, the hole or fixing, the `Mains` item and how far apart they stand against the distance required. A design with no hole is not failed for that. A hole's plating on a net outside `Mains` is otherwise held by the signed rule's copper figures, so the plated-hole rule fires only where the pad's copper is clear of the signed clearance and creepage and its drilled hole is not.

The **mains layer separation** (`mains_layer_separation`) holds `Mains`-class copper apart from every other net's copper on every copper layer. KiCad's own layout check compares copper on one layer only, so inner-layer low-voltage copper, such as a ground plane, a ground fill or a signal track, can lie directly under, or within the signed distance in plan view of, mains copper on the surface, or beside the wall of a barrier slot, and no other rule flags it; a single ply of prepreg between two layers is 0.21 mm and is not reinforced insulation. The check reads `mains_to_low_voltage.clearance_mm` and `.creepage_mm` of the record and judges, from the layout KiCad has just refilled, every pair of one `Mains`-class item and one other item, a pad, a track, an arc, a via, a pour or a copper graphic of any net or of none, on layers KiCad does not compare. Four tests are made. **Clearance:** the straight-line distance between the two seen from above, layers ignored, is at least `clearance_mm`. **Creepage:** the shortest path between them seen from above that does not cross a barrier slot, going round its ends, is at least `creepage_mm`; a barrier slot is a closed cut-out inside the board outline, drawn on `Edge.Cuts`, that is not a round hole, and a notch drawn into the outline's own line is part of the outline and not a slot, so across such a notch the creepage path is the straight line, which is shorter than the way round the notch and so errs toward failing a pair. A closed cut-out whose every corner lies inside the outline or on it, a cut-out flush with an edge included, is a slot whichever corner is written first. The path is the exact shortest one round the corners of the slots, not a grid, and the board's thickness is not added to it. This test fires for any pair under `creepage_mm` apart in plan view on layers KiCad does not compare, not only for a pair a slot lies between: a `Mains` track on the front copper over a low-voltage pad on the back copper 6 mm away fails it where `creepage_mm` is 10 mm. **Overlap:** a low-voltage item whose outline overlaps a `Mains`-class item's in plan view fails whatever the distances are, named as an overlap and not as a clearance. **Pull-back:** every inner-layer copper item of any net, a plated through hole counting as copper on every layer, stands at least 1.5 mm from the wall of every barrier slot, because the wall is exposed glass fibre; this 1.5 mm is a constant of the check (`SLOT_WALL_MM`), not a figure of the record, and surface copper is left to the other rules. A pair that shares a copper layer the layout stores both items on is left to KiCad's own rule, so one fault gives one failure; the layers an item is stored on are those the layout file gives it, the outer layers for a through-hole pad stored on those only and the layers it spans for a blind or buried via. The plated barrel of a through-hole pad or a via is copper on every layer, so the pull-back test holds it as inner-layer copper whatever layers it is stored on. A pour counts by the fill the layout stores, or by its outline on a layer where it stores none; a keepout is not copper; the pads of a mounting hole are held by the `mounting_hole` rule and not here. A copper graphic is measured with its stroke, a filled one to the outer edge of its stroke, and a footprint's graphics on a copper layer are measured like the layout's own. Arcs and circles are read as straight pieces no more than 5 micrometres off the drawn curve, so a way round a slot's round end is read up to that much short, never long. Copper the layout file does not size fails by name: text on a copper layer, a curve drawn on a copper layer (`cannot measure a copper curve`), and a custom or per-layer pad within `creepage_mm` of an item on a layer KiCad does not compare it with. One failure is reported for each test and kind of pair at the nearest, with the number of further pairs, naming both items with their layers and nets, the test, the distance and the figure it falls short of, and for creepage the path length and the slots it goes round. A `between` entry of `accepted_exceptions` with pair `mains_to_low_voltage` excuses the clearance or creepage shortfall of the one pair it names, by pads or by nets, at or above its `accepted_mm`, and fails as `spacing_exception` below it; an overlap and a pull-back are excused by no entry. The rule adds no KiCad run: it works on the layout KiCad has already refilled, so its time is the Python time of the geometry, which finds the nearest sides of two shapes through a tree of boxes over their sides, so two large fills are not compared side by side, and works the corners of the slots once for a run and not once for a pair. A design that declares `MAINS` none is not held by it, and one that declares `MAINS` present with no `mains_to_low_voltage` figures, or whose `Mains` class cannot be resolved, fails under the names those failures already carry.

The layout check enforces the signed figures, not the design's own. On the temporary copy, the record's clearance and creepage are appended to the design's rules, in the same condition form, after every rule the design writes. In KiCad the last matching rule wins, so no rule the design writes and no net class setting can undercut its clearance and creepage constraints. The rules the check itself writes after it can only tighten it: the hole rules hold other constraint types, which it does not decide, and the sensing rules for a pair with `Mains` ([The sensing-clearance and ground-return rules](#the-sensing-clearance-and-ground-return-rules)) hold a clearance of no less than the signed figure. A design that declares a stricter figure is still held only to the record's. After the signed `Mains` rule, in the same manner, the check appends four more: the signed `mains_to_mains.clearance_mm` and `creepage_mm` between any two items of the `Mains` class on different nets; the signed `terminal_clearance_mm` between two pads of the `Mains` class, those of one part and of neighbouring parts; the signed `creepage_ahead_of_fuse_mm` for a pair with an item of the `Mains_Entry` class and an item of `Mains`; and, for each pair in `held_at_reinforced`, the larger of the signed `mains_to_low_voltage` clearance and the `mains_to_mains` clearance, and likewise for the creepage. They come last among the rules the check writes for the separation, so nothing the design writes loosens them. KiCad reports a shortfall as its own clearance or creepage violation naming both nets and the rule, `pre-order check: signed mains-to-mains spacing`, `pre-order check: signed terminal clearance`, `pre-order check: signed creepage ahead of the fuse` or `pre-order check: net pair held at reinforced`. Two items of one net are never reported.

KiCad 10 ranks some settings above every custom rule, and the appended rule cannot outrank them. The check therefore fails them outright:

- **A local clearance override on a pad or a footprint** below the signed clearance fails, whatever net it is on. KiCad 10.0.7 applies the larger of the two items' pad or footprint overrides ahead of any custom rule. A 0.1 mm override on either a mains pad or a low-voltage pad would let low-voltage copper pass at 0.1 mm. A smaller clearance can still be written as a custom rule, which the signed rule outranks.
- **A zone's clearance** does not outrank custom rules: zones are refilled to the signed figure. A zone on a `Mains`-class net may still not declare a clearance below the signed figure.
- **A net tie joining a `Mains`-class net to any net outside the class** fails, naming the footprint and both nets. A net tie joins its nets in copper, so such a tie joins low-voltage copper to mains outright, and KiCad 10.0.7 checks no clearance between the pads it ties. A net tie may join `Mains`-class nets to one another. A pad group naming a pad its footprint does not have fails too, since which nets it joins cannot be told.

## The parts check

Every design is also held to the parts it is specified with and to a dated reading of the manufacturer's catalogue, whether or not it carries mains. The check reads files only and never fetches the catalogue. It reads each part from the schematic, which is the authority for what is ordered; the `LCSC` and `Rating` fields a layout footprint carries are not compared with it.

A design is held to the `parts-specification.yaml` and the `catalogue-extract.yaml` in the nearest folder at or above it, found as the separation basis record is, and each must be committed. A design with neither, one that cannot be parsed, one missing a required key and one that lists nothing each fail as `parts_record`. A file marked `synthetic: true` satisfies only a design marked not for manufacture (`NOT_FOR_MANUFACTURE=true`).

- **Positions the design places** are the schematic symbols that are on the board, in the design's schematic and every sheet it reaches, counted once however many units a symbol has, provided its units agree on Value, footprint library item, `LCSC` and `Rating` (a further unit that differs from the first, or lacks one the first has, fails as `parts_part`, naming the reference and the property); power symbols (by the library symbol's power flag, never by how the reference is written, so a non-power symbol whose reference starts with `#` is a position) and symbols with `on_board` set to `no` are no position. Two symbols carrying one reference, being the same unit of one library symbol or different library symbols, fail as `parts_part`, naming the reference. A sheet used more than once places the references its instances give.
- **The specification record** holds a list under `positions`. Each entry has `reference` and `lcsc` and may have `value`, `package` and `rating`; a property it leaves out is not compared. Each entry also carries `class`, which the derated-voltage rule below reads. The design's value is the symbol's `Value` field, its package the footprint's library item name (what follows the library nickname and its colon), its rating the symbol field `Rating` and its catalogue number the symbol field `LCSC`. A position the manufacturer does not place, such as a hand-fitted connector, test point or link, states its catalogue number as the word `none`, lowercase, in both the record's `lcsc` and the symbol's `LCSC` field, and the two must agree; the check looks nothing up in the catalogue extract for it, consults no stock or lifecycle figure, and still compares its value, package and rating. Only the exact word is `none`: `None`, `NONE` and every other string are catalogue numbers, looked up and failing when the extract lacks them, and an empty or absent field is not `none` and fails as a difference. A part with no `Rating` field fails a record that states a rating for it. Each position the design places that the record omits, and each stated property or number that differs, fails as `parts_part`, naming the position, the property, the record's value and the design's value.
- **The catalogue extract** states `read_on`, the date it was read, `max_age_days`, and a list under `entries`, each with `lcsc`, `library_class`, `stock` and `unit_price`, and a `lifecycle` mapping on the entry of every part the design places, holding all three of `status` (the part's lifecycle status as published: `active`, `not recommended for new designs`, `end of life`, `obsolete`, or `no source publishes one`), `source` (where it was read) and `read_on` (the `YYYY-MM-DD` date it was read); it may also state `source` for readers. An entry may also carry `category`, the first category name of the part's parts-library record (the `firstSortName` field of the JLCPCB parts-library search service's record, copied verbatim; its second category name is not read), a non-empty string when present; the decoupling rule reads it ([The no-supply categories](#the-no-supply-categories)), and an empty or non-string `category` fails as `parts_record`, naming the entry. The lifecycle rule ([The board-minimums and lifecycle rules](#the-board-minimums-and-lifecycle-rules)) reads the mapping. An entry key other than these (`lcsc`, `library_class`, `stock`, `unit_price`, `lifecycle` and `category`), or inside `lifecycle`, fails as `parts_record`, naming the key. A part whose `LCSC` number is not among the entries, or whose entry has a stock of 0, fails as `parts_catalogue`, as does an extract read more than `max_age_days` days before the day of the check, one dated later than the day of the check, an entry whose `stock` is not a whole number of at least zero and a catalogue number that two entries both carry. An entry showing a stock of 0 is a legitimate entry that fails only a part using it. A board's design task authors its record and extract and keeps the extract current for the parts the board uses.

## The derated-voltage and pin-limit rules

Two further rules read the design's schematic, the parts specification record, the derating policy and the pin-limit record, and share one reading of the voltage each net can reach. They read files only. A part's kind is read from its reference designator, as a connector's is: the leading letters of the designator are matched whole: `U` is an integrated circuit, `D`, `Q` or `LED` a semiconductor, `FB`, `L` or `F`, or `R` with the value zero, a part that joins nets, and every other designator (`FID`, `FL`, `LCD`, `LS`, `DS` and the rest) a passive or mechanical part. The part's `class` plays no part in deciding kind.

- **What a net can reach.** The pin-limit record lists power domains, each with a `rail` (a net) and a `highest_voltage_v`, and, per part by `lcsc` number, the pins with the `domain` each belongs to. The highest voltage a net can reach is the largest of its rail's `highest_voltage_v`, the domain voltage of every listed pin on it, and that of any net joined to it, directly or in a chain, through a part that joins nets. A resistor or capacitor joins nothing, so a divider or a decoupling capacitor never lifts a net to the rail it hangs from. The lowest is the smallest of 0 V for a rail of any domain other than a mains domain, minus the domain's `highest_voltage_v` for a mains domain, since mains alternates, and the lowest of every listed pin's domain on it. A mains domain is a domain whose rail is on a net of the `Mains` class. A connector pin driven from outside the board is declared in the connector's entry.
- **Derated voltage** (`derated_voltage`). Every position of the parts specification record carries `class`, naming a class of the derating policy exactly, or `none` for a part no class covers and whose rating, in the record and in the design's `Rating` field, states no figure in `V`, `VDC` or `VAC`; a part with such a figure that names `none` fails. A position with a class has a rating written as a figure with unit `V`, `VDC` or `VAC` in both the record and the design's `Rating` field (an AC figure is taken at its peak, the figure times the square root of two). The part's working voltage is the largest, over every pair of nets it connects, of the difference between their highest voltages, except that a pair whose two nets both take their highest voltage from a mains domain counts as the largest `highest_voltage_v` of a mains domain on either net, whichever net the part names first, since a part across them sees the mains swing, unless one net rides on the other's domain or both ride on one host by `rides_on`, when the pair counts as the difference of the voltages so derived (two nets of one host with no stated relation still count the host's full `highest_voltage_v`). The rule fails a part whose working voltage exceeds the policy's voltage share times its rating, and a covered part with a net whose voltage cannot be worked out, which is reached only through resistors or capacitors with no rail or listed pin, until that net is declared as the rail of a power domain. A design that declares mains present needs a pin-limit record with a mains domain whose `highest_voltage_v` is at least the peak of the basis `working_voltage`, which is read as an rms figure at the top of the declared supply span; a mains domain with `rides_on` is held instead to its derivation from its host, which meets that floor directly or through its own hosts in turn. The power and temperature shares are not judged.
- **Owner-accepted derating exceptions** (`derating_exception`). The derating policy record may list `accepted_exceptions`, each entry a mapping of exactly `position` (a reference designator the design's schematic places), `accepted_v` (the working voltage in volts the owner accepts, a positive number), `reason` (the owner's ground), `bounded_by` (the independent element that bounds the fault the stress could cause, or, for a position whose stress the rule overstates, the figure that bounds it), `accepted_by` and `accepted_on`; the key is optional and an explicit empty list is a record that accepts none. A position whose working voltage exceeds its limit passes when its entry is signed and its `accepted_v` is no less than the working voltage the rule worked out, and the check prints an `ACCEPTED` line naming the entry, the position, the working voltage, the limit, the accepted figure and the reason; the same position with no entry, or with an `accepted_v` below its working voltage, fails as `derated_voltage` (naming the entry where there is one). An entry excuses nothing but its own position, so a second part over its limit stays a failure. An entry fails as `derating_exception`, naming it, when its `accepted_by` is empty, a placeholder or in angle brackets, or its `accepted_on` is empty, not a `YYYY-MM-DD` date or later than today; when its `position` is no position of the design's schematic; when its `accepted_v` does not exceed the position's limit, so the part needs no excuse; and when no position's failure uses it, so it is stale. An unsigned entry excuses nothing, so its position keeps its `derated_voltage` failure beside the entry's own. An entry that is not a mapping of exactly those keys, repeats a position or gives a non-positive `accepted_v` fails the record as `derating_record` instead and the rule does not judge a record that has already failed; a record marked synthetic is honoured only for a design marked not for manufacture. `accepted_by` and `accepted_on` are the owner's: nothing in the check or the record is signed by a tool or an agent, a drafted entry stays unsigned until the owner signs it, and the check fails an unsigned draft, which is the intended state of a draft. A part standing across a series midpoint, such as a discharge resistor across the midpoint of line and neutral, sees a share of the mains the rule over-reads, because `rides_on` names one host and a midpoint of two hosts cannot be stated; it is excused by an entry that states the real stress and its ground, not by a second `rides_on` host, and the owner signs that ground, which the check does not test.
- **Pin limits** (`pin_limit`). Every integrated circuit and semiconductor the design places has an entry in the pin-limit record, found by its `LCSC` number; a passive or mechanical part needs none. A listed pin fails where its net can exceed its `absolute_max_v` or fall below its `absolute_min_v`, and where its net is driven from another domain whose `highest_voltage_v` is above zero while `tolerates_driven_unpowered` is false. A listed pin the placed part's symbol does not have fails, by its number or its name; a real pin left unconnected is a pin the part has. Every connected pin of such a part needs its own entry, and a connected pin the entry omits fails, naming the part, the pin and the part's catalogue number. A pin is connected when its net holds another pin, of the same part or of any other part, or is the rail of a declared domain; a pin on no other pin and no rail needs no entry. An entry covers only the pin it names, by number or name, and stands for no other. A pin whose datasheet limit is a current takes an entry like any other, holding the datasheet's voltage ratings or, where it states none in a direction, the lowest or highest voltage of the domain that drives its net; the current is not judged. A part the record omits altogether is reported once by the omission failure, not again for each pin. Power limits are not judged. A figure is compared with a relative slack of 1e-9.

The rating's unit (V, VDC or VAC) and a reference designator's leading letters are read ignoring letter case, so `630Vdc` is a figure and `u1` is an integrated circuit. A missing record the rule needs fails; a design with no integrated circuit, semiconductor or covered part is not failed for that, and `none` as a class is accepted for a part whose rating states no figure in V, VDC or VAC. A record that has already failed as `derating_record`, `pin_limits_record` or `parts_record` is not judged again. Each failure names the rule, the design and the offending position, pin, net or record key.

## The sensing-clearance and ground-return rules

Two further rules read the layout, the project file's net classes and the **board rules record**, `board-rules.yaml`, in the nearest folder at or above the design, found as the separation basis record is and committed. Every design needs one: a design whose folders hold none fails as `board_rules_record`, and so does one whose record is silent on either mapping or on `fabrication`. The record holds the two mappings `sensing` and `ground_returns`, and the `fabrication` mapping that [the board-minimums rule](#the-board-minimums-and-lifecycle-rules) reads, and may be marked `synthetic: true`, which passes only a design marked not for manufacture. Each mapping may instead be the word `none`, which a design with no sensing net class, or no connector whose signals the ratio governs, states and the check accepts; the check does not infer classes from net names, so a design cannot be passed by what it leaves out of a mapping, only by stating `none`.

- **Sensing clearance** (`sensing_clearance`). The `sensing` mapping holds `classes`, the net classes that carry precision sensing, `noisy_classes`, the net classes that switch or drive loads, `clearance_mm`, a positive number of millimetres, and `source`, where the figure was read from. A class is named once, in one of the two lists, and must be a net class of the project file that holds at least one net on the layout, so a misspelt class fails rather than leaving its rules applying to nothing. The layout check runs a second time on the temporary copy with one rule for each sensing and noisy class pair, and a sensing item closer than its pair's figure fails, reported under the pair's own rule name. A pair without the `Mains` class is written after the design's own rules and ahead of the signed rule, at `clearance_mm`. The signed rule's condition already matches a pair with `Mains` and, being last, would decide its clearance and hide a sensing figure above the signed one, so that pair's rule is written after the signed rule, holds a `clearance` constraint alone at the larger of `clearance_mm` and the signed clearance, and can only tighten; the signed creepage stays with the signed rule. The design's own rules are checked as the design wrote them in the first run, so a pair the design holds more strictly is still held to its own figure there. Findings of the second run are read by rule name only.
- **Sensing override** (`sensing_override`). KiCad ranks a pad's or a footprint's local clearance override above every custom rule, so one below `clearance_mm` on a sensing or noisy class net would let a sensing item pass closer than declared. A pad on such a net with an override below the figure fails, and so does a footprint with such an override that has any pad on such a net. A pad on no net is not counted. This check does not wait for a signed figure, so a design that declares `MAINS` as `none` can still declare sensing classes, and it is separate from `local_clearance_override`, which fails an override below the signed figure on any net.
- **Ground returns** (`ground_return`). The `ground_returns` mapping holds `ground_classes`, the net classes that are returns, `non_signal_classes`, the net classes such as power rails and `Mains` whose pins the ratio does not apply to (a list that may be empty), and `signal_classes`, a list with one entry for each signal net class, each holding `class`, `signal_pins_per_return` and `source`. `signal_pins_per_return` is a positive whole number, the most signal pins one ground-return pin may serve, so a smaller number is stricter. A connector is a part whose reference designator begins with `J`, a connector-prefixed jumper included. Its pins are the numbered pads of its footprint that sit on a net, counted once however many pads carry a number; a pad with no number is no pin on a ground class, so it is never a ground return, while one on a signal class counts as a signal pin of its own, and one on a non-signal class is not counted; a pad on no net, and one on a net named `unconnected-(…)` that no other pad on the board carries, is no pin (a net of that name carried by two or more pads is a real net and its pads are pins). A pin's classes are the project file's classes KiCad places its net in, or `Default` where it is in none. A pin on a ground class is a ground-return pin, one on a signal class a signal pin, and one on a non-signal class neither. The rule fails a connector whose signal pins exceed the smallest `signal_pins_per_return` among the signal classes it carries times its ground-return pins, compared exactly on whole pins, so a connector with signal pins and no ground-return pin fails. A pin whose classes the mapping declares as none of ground, signal and non-signal fails, naming the class and the pin, and so does one whose net is in classes it declares as more than one of them. `Default` is a class like any other and is declared where a design leaves signals on it. A design with no connector is not failed for that, and parts that are not connectors are not judged; signal integrity beyond the declared ratio is not judged.

Each failure names the rule, the design and the offending item: the two items and their nets, the pad and part, the connector with its signal and ground-return pins, or the record key. The design's record is read in the one form of the table below. A record that has already failed as `board_rules_record` is not judged again. The layout practice catalogue's sensing item `SENSE-6` in [`docs/board-design-method.md`](../docs/board-design-method.md#sense-6-sensing-nets-keep-the-declared-clearance-from-switching-and-drive-nets) is the enforced counterpart of the reviewer's `SENSE-4`.

## The board-minimums and lifecycle rules

Two further rules hold a board to a dated reading of what its manufacturer makes, and to the lifecycle status the catalogue extract states for each part the board places. Both read files only; neither fetches anything, and neither reads firmware.

**The manufacturer limits record**, `manufacturer-limits.yaml`, is found as the separation basis record is, the nearest at or above the design's folder, and committed. It holds `read_on`, the `YYYY-MM-DD` date the limits were read; `source`, where they were read; `max_age_days`, a whole number of days above zero beyond which the check refuses the record; and `processes`, a non-empty list. Each process holds `copper_layers`, a whole number; `outer_copper_oz`, the finished outer copper weight in ounces, a positive number; and `limits`, a mapping from the name of the board-setup minimum it bounds, as KiCad names it (`min_track_width`, `min_clearance`, `min_through_hole_diameter`, `min_hole_to_hole`, `min_via_annular_width`, `min_via_diameter`, `min_hole_clearance`, `min_copper_edge_clearance` and the like) to a mapping of `mm`, the limit in millimetres, a positive number, and `citation`, a mapping of `section`, `limit` and `condition` that names the entry of the dated prose record of the manufacturer the figure was read from: the heading its table sits under, its Limit cell and its Condition cell, since several entries share one source. A process is keyed by `copper_layers` and `outer_copper_oz` together and listed once. A record marked `synthetic: true`, as the one in `hardware/proof/` that serves the throwaway designs is, passes only a design marked not for manufacture. A test holds each figure of a record not marked synthetic to the matching entry of the dated prose record its `source` names (for JLCPCB, [`docs/board-manufacturer-jlcpcb.md`](../docs/board-manufacturer-jlcpcb.md)), so the record cannot drift from the page it was read from; a synthetic record is exempt. The figures, and the copper weight, of a real board are that board's design task's to choose and cite.

**The fabrication mapping** is the board rules record's third mapping, beside `sensing` and `ground_returns`. It holds `outer_copper_oz`, the finished outer copper weight in ounces, a positive number, and `source`, why that weight was chosen. Unlike the other two it may not state `none`, and silence fails: the manufacturer takes the weight as an order option and no layout file carries it, so the weight is declared where the order is decided. **The copper weight declared there is the weight the order must select**: the board is held to the limits of that weight, so ordering another one orders a board the check never judged. JLCPCB's standard weight, 1 oz, carries no surcharge and a heavier one multiplies the price, so a heavier weight needs its `source` to say why.

- **Board minimums** (`board_minimums`). A design's process is its layout's copper layer count, read from the layout's own layer stack, together with the weight its `fabrication` declares. The rule fails a board whose process the record does not list, and, for the limits of the process it does, a board-setup minimum (`board.design_settings.rules` in the project file) smaller than the limit of the same name, a board-setup minimum the limits bound that the project file does not state at all (naming the key, since KiCad would then apply its own default, which no record reviews), a net class whose `clearance` or `track_width` is smaller than the limit of `min_clearance` or `min_track_width`, and a minimum that a custom rule's constraint sets smaller than the limit of the board-setup key the constraint maps to: `clearance` to `min_clearance`, `track_width` to `min_track_width`, `hole_size` to `min_through_hole_diameter`, `hole_to_hole` to `min_hole_to_hole`, `annular_width` to `min_via_annular_width`, `via_diameter` to `min_via_diameter`, `hole_clearance` to `min_hole_clearance` and `edge_clearance` to `min_copper_edge_clearance`. Looser means smaller, and a figure at the limit passes. A rule's figure is converted to millimetres from the unit it is written in (`mm`, `mil` or `in`, or a bare number of millimetres); one written in another form fails, since it cannot be shown to be no looser. Any other constraint, such as `track_angle`, `creepage` or `courtyard_clearance`, is not judged, and neither is a minimum the process does not bound. Nothing exempts a design: a design whose folders hold no manufacturer limits record, one whose record is not tracked, unreadable, not in its form or synthetic on an orderable board, one read more than its own `max_age_days` days before the day of the check or dated later than it, all fail as `manufacturer_limits_record`, and one whose board rules record declares no `fabrication.outer_copper_oz` fails as `board_rules_record`, naming the key.
- **Lifecycle** (`parts_lifecycle`). The catalogue extract's `lifecycle` mapping, holding `status`, `source` and `read_on`, is required on the entry of every part the design places; an entry no placed part uses may leave it out. A placed part whose entry lacks it fails, naming the position and its catalogue number. A status other than `active`, `not recommended for new designs`, `end of life`, `obsolete` or `no source publishes one`, or a mapping missing any of its three keys, fails as `parts_record`. A part whose status is `end of life`, `obsolete` or `not recommended for new designs` fails, and so does one whose lifecycle `read_on` is more than the extract's own `max_age_days` days before the day of the check or later than it. A status of `no source publishes one` is not failed for that, because its `source` names the sources that were looked at. A part the extract does not list fails as `parts_catalogue` and is not judged again here. Choosing a replacement part is the designer's.

Each failure names the rule, the design and the offending item: the process, the record key or figure, the net class, the custom rule and its line, or the position and its catalogue number. A record whose form has already failed as `manufacturer_limits_record` or `board_rules_record` is not judged again; one that is only too old is still compared, so its failure and the board's are reported together.

## The one form each file is read in

Wherever KiCad can answer a question, the check asks KiCad: which nets are in `Mains`, whether the rules file loaded, what a zone fills to, whether a symbol's or footprint's library is reachable. Where the check has to read a file itself, it reads it only in the one form KiCad writes, and fails any other form by name rather than guessing what KiCad would make of it:

| File | The form read | Anything else fails as |
|---|---|---|
| Custom rules (`.kicad_dru`) | Each rule has its own name, and at most one `(condition ...)`, one `(layer ...)` and one `(severity ...)`. KiCad loads a rule with two conditions and keeps only one of them, and loads two rules of one name. | `custom_rules` |
| The Mains rule in it | Exactly one condition, written exactly `A.hasNetclass('Mains') && !B.hasNetclass('Mains')`, with no other spacing; exactly one `(constraint clearance (min <n>mm))` and one `(constraint creepage (min <n>mm))`, in millimetres with no further limit; no other constraint. | `separation_rule` |
| Project file (`.kicad_pro`) | Every key once in each object; `text_variables` an object of strings; `NOT_FOR_MANUFACTURE` `true` or `false` when present; the exclusion lists lists; `net_settings.netclass_assignments` an object; `net_settings.classes` a list, each class's `track_width` a positive number or left out, when it takes the `Default` class's. Its net classes and patterns are resolved by KiCad itself. | `project_file` |
| Separation basis record | Every key once and no YAML merge key (`<<`); only the keys listed below, plus any further pair of distances for readers, a mapping holding exactly `clearance_mm` and `creepage_mm`; `mains_to_low_voltage` holding only those two; `mains_to_mains` holding only `clearance_mm`, `terminal_clearance_mm`, `creepage_mm`, `creepage_ahead_of_fuse_mm`, `entry_fuse`, `held_at_reinforced` and `downstream_basis`, the first six required of a mains-present design's record, bar a fixture's that carries no mapping (see `MAINS_ENTRY` above); `overvoltage_category`, `altitude_m`, `barrier_types` and `table_rows`, when present, in the forms described above, with no key inside them that is not named there; `accepted_exceptions`, when present, a list of entries each holding exactly `pair`, `constraint`, `between`, `accepted_mm`, `reason`, `bounded_by`, `accepted_by` and `accepted_on`, or, for a `same_connector_pins` entry, exactly `pair`, `constraint`, `connector`, `pitch_mm`, `accepted_mm`, `reason`, `bounded_by`, `accepted_by` and `accepted_on`, or, for an entry holding `nets_a`, exactly `pair` (`mains_to_mains` only), `constraint`, `nets_a`, `working_voltage_v`, `accepted_mm`, `reason`, `bounded_by`, `accepted_by` and `accepted_on` and optionally `nets_b`, with no `between`, each in the form described above; `synthetic` `true` or `false` when present. | `separation_basis` |
| Pin allocation record | Every key once and no YAML merge key (`<<`); the key `channels` a non-empty list; each entry a mapping, read for the keys `channel`, `net`, `controller_pin`, `connector`, `connector_pin`, `far_channel` and `rail` and for no others; `controller` the word `none` when present, which declares that the design places no controller, and then each entry exactly one of `far_channel` and `rail`, with `connector` and `connector_pin` and no `controller_pin`; a rail entry carrying no `controller_pin` and a record not declaring `none` listing at least one channel with one; `synthetic` `true` or `false` when present. | `pin_allocation` |

### How a class is read

The pre-order check, the locked-copper commands and the review views all learn which nets are in a net class the same way. KiCad's layout check runs on boards holding nothing but one track for each net of the layout. Each board is opened with the layout's project file and carries the `(net_class ...)` blocks the layout file holds, so KiCad applies the project file's assignments and patterns and the layout's own classes exactly as on the layout. One assertion rule per class fails on every track KiCad places in that class, and a marker rule fails on the one track laid on the back copper, which shows KiCad loaded the rules. The project file's own `Mains` nets are read the same way, without the layout's classes.

KiCad 10.0.7's command-line layout check reports at most 199 failures of one kind and drops the rest at random. A board of one track per net reports each net once per class, however much copper it carries, and the nets are split into batches small enough that a run's marker and class reports stay below that limit; the batches' answers are merged. A run whose reports still reach the limit is refused, naming the class and the limit, rather than read as complete. A correct batching never reaches it. The limit is stated once in `board_check.py`, and a test against the installed KiCad confirms it.

## The report

The report has one verdict line per design, one line under it for each measured rule's figure (the workmanship rules', the barrier's, the paste's, the pour gap's, the test point to courtyard distance's, the three inherent zeros of `DECOUPLE-6`, `MFG-7` and `MFG-9`, the fiducial count of `MFG-10`, the sensing clearance of `SENSE-6` where the design declares one, and the count of decoupling paths `DECOUPLE-6` measured), one `ACCEPTED` line for each spacing exception the owner signed that the layout uses (the entry, the pair and constraint, the items or the lists of nets, the measured and accepted distances, the figure the exception relaxes, the owner's reason and the element that bounds the fault, so an accepted shortfall is never silent), one line per violation, and a result line last. The report has the one text form; there is no machine-readable form:

```
DESIGN | hardware/proof/gate-proof/gate-proof.kicad_pro | PASS
FIGURE | hardware/proof/gate-proof/gate-proof.kicad_pro | WORK-2 route length | WORK_DETOUR_RATIO | 1.3 times the shortest straight-line tree joining the net's pads
DESIGN | hardware/m/board/board.kicad_pro | FAIL | 1 violation
VIOLATION | hardware/m/board/board.kicad_pro | clearance | Track [/LV_A] on F.Cu, length 2.0000 mm @ (28.085, 9) mm; PTH pad 2 [/MAINS_N] of R1 @ (25.16, 10) mm | Clearance violation (rule 'pre-order check: signed separation basis' clearance 3.0000 mm; actual 2.0000 mm)
RESULT | FAIL | 1 of 2 designs failed
```

Each figure line has five fields separated by ` | `: `FIGURE`, the design, the item and what it measures, where the figure is read from (a project text variable, a Board Setup value, the rules file, or `none, inherent zero`), and the figure read with its unit. Each violation line has five fields separated by ` | `: `VIOLATION`, the design, the rule broken, where it is, and the message. The message is KiCad's own for anything KiCad found, and says what to change for anything else. The crystal keep-clear (`CLOCK-4`), the ground pad reliefs (`MFG-5`) and the floorplan's regions (`FLOOR-4`) are custom rules in the design's rules file that KiCad enforces, and the check reports what KiCad finds: a `courtyards_overlap` violation naming the rule `Crystal keep-clear`, a `starved_thermal` violation where a relief cannot form spokes, and an `items_not_allowed` violation naming a region's rule. The check also holds the first two rules to being there, since a rule KiCad is never given enforces nothing. A footprint whose name begins `Crystal_` or `Resonator_` is a crystal, and its reference needs a rule whose one condition is `A.Reference == '<crystal>'` followed by `B.Reference != '<part>'` for each exempt part, whose one constraint is `courtyard_clearance` at 10 mm or more, with no layer or severity, and which leaves at least one other footprint of the layout unexempted (`crystal_keepclear`). Any other `courtyard_clearance` rule that names the crystal fails for it, because KiCad may apply it after the keep-clear and loosen it. The one mention that does not name a crystal is a `B.Reference != '<part>'` clause inside a rule whose whole condition is the keep-clear form for another reference, since inside that form a `!=` only removes pairs from the rule: on a board of two crystals each keep-clear exempts the other and passes, and a keep-clear for the second below the floor is reported once, for the second. Every other mention counts as naming the crystal: `A.Reference ==` or `B.Reference ==` anywhere, including `A.Reference == '<second>' && B.Reference == '<first>'`, and a `!=` in any form but that one, because KiCad evaluates a rule's condition for both orders of a pair, so `A.Reference != '<crystal>'` and a bare `B.Reference != '<crystal>'` each loosen the keep-clear. A net class whose name contains `ground` or `gnd`, in any case, with a pad on one of its nets that is not its footprint's exposed pad (the strictly largest pad of a footprint of more than two), needs a rule whose one condition is `A.Type == 'Pad' && A.hasNetclass('<class>')` followed by one `&& !(A.Reference == '<part>' && A.Pad_Number == '<n>')` for each exempt pad, whose one constraint is `zone_connection thermal_reliefs`, and which exempts only exposed pads on nets of the class (`ground_relief`). The check does not judge the floorplan's region rules: which regions a board has, and which parts each lists, come from its own plan, so whether each region has its rule, drawn at the region's bounds and listing the plan's parts, is judged from `layout-plan.md`, `design-rules.md` and the layout review, and the check reports only an `items_not_allowed` violation of a rule the file holds.

The exit status is 0 when every design passes, 1 when any fails, and 2 when the check cannot run at all, for example because a tool is missing.

## The proof designs

`hardware/proof/gate-proof` is a deliberately tiny board. Two mains nets run through a connector and a resistor, and two low-voltage nets do the same, the low-voltage pair also reaching two pins of a controller-style part with named pins, `U1`. Its symbol and footprint libraries are carried beside it, so it needs nothing from a local KiCad installation's libraries. It is marked `NOT_FOR_MANUFACTURE=true`, declares `MAINS_ENTRY` as `present` with `/MAINS_L` in the net class `Mains_Entry`, and carries its own synthetic `separation-basis.yaml` (its `mains_to_mains` figures chosen so the board's own spacing passes), `pin-allocation.yaml`, `controller-part.yaml`, `parts-specification.yaml`, `catalogue-extract.yaml` and `board-rules.yaml` (which states `none` for both mappings, the design having no sensing or ground net class; the parts carry `LCSC` and, on its resistors, `Rating` fields), and its rules file and project text variables carry the workmanship rules, each figure's source given in its rules file. Its reference designators are all on the front silkscreen (`MFG-7`), and it has no pin types, so the decoupling rule (`DECOUPLE-6`) has nothing to measure on it; `task hw:prove` gives its throwaway copy a capacitor across typed power pins with a via between, and a reference moved to the fabrication layer, to prove those rules catch what they guard against. Its separation basis states the inputs and the two table rows the separation floor reads, and it has no mounting hole, which the check does not fail it for; `task hw:prove` adds a hole, a plated hole and a fixing's courtyard inside the signed distance of its mains pads, and moves the record's rows and inputs, to prove the floor and mounting hole rules. It passes the check as committed, and `task hw:prove` shows each failure condition above failing on a copy of it.

`hardware/proof/record-keys-proof` proves the keys the records carry rather than the check's rules. It is a copy of `gate-proof`'s board, marked `NOT_FOR_MANUFACTURE=true`, with its own synthetic records, each marked `synthetic: true` and each carrying every key its decision defines: a `separation-basis.yaml` with `overvoltage_category`, `altitude_m`, two barriers with their `barrier_types` entries, its `table_rows`, and a `mains_to_mains` holding every key including `downstream_basis`, a `derating-policy.yaml`, a `pin-limits.yaml`, a `catalogue-extract.yaml` whose entries carry `lifecycle`, the `pin-allocation.yaml`, a `controller-part.yaml` and `parts-specification.yaml`, and a `board-rules.yaml` that states `none` for both mappings. Its values are generic and cite no real standard's table. It passes the check as committed, and `task hw:prove` seeds a misspelt key into a throwaway copy of it, one in each kind of record that has new keys (a separation basis key, a key inside a barrier entry, a derating policy share, a pin limit and a catalogue lifecycle), and requires the check to fail naming that key. It also seeds the faults of the derated-voltage and pin-limit rules into a copy of it (a resistor across the mains pair rated below the policy's share of the mains peak, a position with no class, a position naming a class the policy lacks, a pin whose net can exceed its `absolute_max_v`, a pin whose net can fall below its `absolute_min_v`, a pin driven from another domain that does not tolerate it, a rated position naming the class `none`, a listed pin the part does not have, and an integrated circuit the pin-limit record omits), and requires each to fail under its rule. It also seeds the riding-domain keys into a copy of it (a part across a divider's tap and its reference whose difference exceeds its share, a riding mains domain on a host below the mains floor, and each malformed declaration: a `rides_on` naming no listed domain, naming its own domain or forming a cycle, a `fraction` or `offset_v` without `rides_on`, both together, a `fraction` of zero or above 1, an `offset_v` of zero or one leaving the derived figure not above 0, a `highest_voltage_v` that differs from the derived figure, and a misspelt riding key), and requires each to fail naming the domain and the key. It also seeds the faults of the owner-accepted derating exceptions into a copy of it, whose tracked `derating-policy.yaml` states no `accepted_exceptions` (the key is optional) and is not edited for them (an over-limit part with no entry, an entry below the working voltage, an unsigned entry, an entry for no position, an entry for a part within its limit, an entry no failure uses, and an entry for one part beside a second over-limit part), and requires each to fail under its rule; the entries it seeds are signed with a made-up name, never the owner's. `task hw:prove` also requires the design itself to pass before it counts a fault caught.

`hardware/proof/review-proof` proves the layout review step of [`docs/board-design-method.md`](../docs/board-design-method.md#layout-review) rather than the check. It is a four-layer board carrying at least one part for every area of the method's layout practice catalogue: a mains terminal and a phototriac with load-side pads, a regulator, a controller with its decoupling and crystal, an exposed-pad part, a current-sense shunt and amplifier, a ferrite bead, a supply input and a load connector each with a transient suppressor or a filter capacitor, test points, mounting holes, ground planes and every floorplan region. It carries one footprint of its own, `review-proof.pretty`, whose paste openings leave a strip for the exposed pad's thermal vias. Beside it are its floorplan and plan (`layout-plan.md`), its rules table (`design-rules.md`) and the synthetic records they read their figures from (`constraints.md`, `separation-basis.yaml`, `pin-allocation.yaml`, `controller-part.yaml`, `parts-specification.yaml`, `catalogue-extract.yaml` and `board-rules.yaml`). Its `board-rules.yaml` is the only one that states both mappings, the design being the only one with a sensing net class and a ground net class: `Sensing` is held 0.5 mm from `Mains` and `Power`, and every connector pin is on `Mains`, `Power` or `Ground`, none on `Default` or `Sensing`, so no connector carries a signal pin and the ratio holds them trivially. `task hw:prove` seeds the sensing-clearance and ground-return faults into a throwaway copy of it, adding the copper, the local overrides and the connector each fault needs, or editing the record. It is laid out clean, is marked `NOT_FOR_MANUFACTURE=true`, and passes the check as committed.

`task hw:review-seed -- --seeds <file> --out <folder>` copies it into a temporary git work tree outside the repository, as `task hw:prove` copies `gate-proof`, and places layout defects in the copy, one or more for every catalogue area, each of a kind only the layout review can see. It runs the check on the copy and refuses it unless the check passes it, since the review step begins only once the check passes a board. It then writes the review folder, which must be new or empty and outside the repository, holding only what the review step gives a reviewer: the seeded copy's KiCad files at `hardware/proof/review-proof/` with its floorplan and plan, its rules table and the records that table reads its figures from, and never the design's own review record or any other file of its folder, the method as written, this readme, every view `task hw:views` renders of the copy (in `views/`), the placement view and measures `task hw:placement` renders of the copy (in `placement/`) and the check's report on the copy (`check-report.txt`). The design and the documents are taken as the last commit holds them. Nothing in the folder tells a seeded item or file from an unseeded one but the defect itself: each item a seed adds takes a fresh random identifier of the form KiCad gives the design's own, KiCad itself refills and saves the seeded layout so every item sits in its order and form, the design folder holds none but the committed design's files, and every file and folder carries the same time. The seed list is written to `<file>` as JSON, giving for each seed its identifier, the catalogue item that covers it, its layer, its board position in millimetres and what it is; it is refused inside the review folder or inside any design's folder. `task hw:review-seed -- --print-prompt` prints the fixed prompt a blind review of the folder is started with, which names nothing seeded. The command prints `REFUSED` lines and exits 1 when it refuses, prints `CANNOT RUN` and exits 2 when a tool is missing, and exits 0 when the folder and the seed list are written. With `--keep-work-tree <folder>`, a new folder outside the repository and apart from the review folder and the seed list, it keeps the seeded copy's git work tree in `<folder>/repository` instead of deleting it with the temporary folder and prints a `KEPT` line naming it and the commit; a command that does not finish keeps nothing. The fanned-out layout review is proven on that work tree ([The layout review by unit](#the-layout-review-by-unit)), and without the flag the command, its folder and its tests are as they were.

`hardware/proof/circuit-review-proof` proves the schematic review step of [`docs/board-design-method.md`](../docs/board-design-method.md#schematic-review), the counterpart of `review-proof` for the circuit rather than the layout. It is a clean, circuit-correct board marked `NOT_FOR_MANUFACTURE=true`, drawn separately from the other proof designs, which it extends none of. It declares mains and carries a heater triac driven through a phototriac from a small controller, with a supply inlet, fuse, varistor and filter capacitors, a regulator and its supervisor, a debug header, an I2C connector and a sense input, and holds at least one part or net for every circuit practice catalogue item a condition selects. It carries its own synthetic `separation-basis.yaml` (with its per-barrier insulation types and table rows), `derating-policy.yaml`, `pin-limits.yaml`, `parts-specification.yaml`, `pin-allocation.yaml`, `controller-part.yaml` and `catalogue-extract.yaml`, a `board-rules.yaml` that states `none` for both mappings (its ground is in the `Default` class, so there is no ground net class to count returns on), its constraints, circuit-proof and bring-up records, and a laid-out board, since the check requires one beside every project; the schematic review judges the schematic only. Its parts are real parts whose datasheets are published, because the review opens every datasheet at its address. It passes the check as committed. It has no seeding command. Its copy is seeded by a session that has not read the catalogue, working on a copy of the design's folder in a temporary work tree outside the repository: it keeps the copy's records consistent, commits the copy and writes the seed list apart from both the copy and the review folder. The blind review is a fresh session, granted read tools and read-only retrieval of a datasheet, in a folder holding the seeded copy at its repository-relative path, its netlist, its records, the drawing of each sheet, the method, this readme and the check's report on the copy; `task hw:schematic-review-folder` writes it, and `task hw:schematic-review-proof` runs the fanned-out form on it ([The schematic review by unit](#the-schematic-review-by-unit)).

The same design also proves the method's [ordering step](../docs/board-design-method.md#ordering), which checks a board's production files before it is paid for. `task hw:production-seed -- --seeds <file> --out <folder>` exports the design's production files from the last commit with the commands the step names, in a temporary work tree outside the repository, and seeds known defects into the placement file converted from the position export by `hardware/tools/production_files.py placement`, into the parts list, and into the fabrication layers exported from an edited copy of the board. A seed whose file or row is the same after it as before does not land, and the command refuses it, writing nothing. It then writes the production-files folder, which must be new or empty and outside the repository, holding only what the step gives a follower: the seeded files in `production/` (`placement.csv`, `parts-list.csv` and the Gerber and drill files in `production/gerbers/`), the image of every fabrication layer and of the drill file that `hardware/tools/production_files.py render` draws from those files, with their index, in `production/layers/`, the drawing of every footprint the board carries at rotation 0 that `hardware/tools/production_files.py footprints` draws, with its index and the rule for reading a placement file's rotation against it, in `production/footprints/`, the unseeded design's views and placement view (`views/` and `placement/`), which stand in for the assembler's own preview because that needs an account and an upload that a read-only session cannot make, the design's `parts-specification.yaml` at its path, the method as written, this readme and the manufacturer's record. Every file and folder carries the same time, and nothing in the folder names the repository or a seed. The seed list is written to `<file>` as JSON, giving for each seed its identifier, the area it covers, the part or layer and what it is; it is refused inside the folder or inside any design's folder. `task hw:production-seed -- --print-prompt` prints the fixed prompt a blind follow of the folder is started with, which names nothing seeded. The fanned-out check ([The production-files check by unit](#the-production-files-check-by-unit)) is proven blind on this folder, a fanned-out run of its own, with the folder written through `task hw:production-review-folder` and the design's views standing in for the assembler's preview as they do here; until that run is recorded the method relies on the single-reviewer form of the check. It prints `REFUSED` lines and exits 1 when it refuses, prints `CANNOT RUN` and exits 2 when a tool is missing, gerbonara at another version than 1.6.3 included, and exits 0 when the folder and the seed list are written.

`hardware/tools/production_files.py` is the step's three commands that `kicad-cli` cannot be: `placement --positions <file> --out <file>` converts KiCad's position export into the assembler's placement file (`Designator,Mid X,Mid Y,Layer,Rotation`), and `render --gerbers <folder> --out <folder> [--resvg <program>]` draws every exported Gerber layer and the drill file into a PNG of its own in one common frame, with an `index.txt` and an `index.json`; it runs under `GERBONARA_PYTHON`; and `footprints --board <file> --out <folder> [--kicad-cli <program>] [--resvg <program>]` draws every distinct footprint the board carries at rotation 0, with its pad numbers and its first-pin and polarity marking, into a PNG of its own, with an `index.txt` and an `index.json` that list each image, the designators that carry it and the rule for reading a rotation against it. Each prints one line per step and a `RESULT` line, and exits 0 when it writes, 1 when it refuses its input and 2 when it cannot run.

## Re-deriving the separation basis for a different supply or altitude

`hardware/sunbeam-em7000/separation-basis.yaml` states its figures against one declared supply (230 V nominal, 216 V to 253 V, 50 Hz), at 2000 m. Someone on a different supply or at a different altitude re-derives it; they do not inherit it. You need only this repository and the public sources the record cites, no Staircase engine.

1. Copy the record into your own machine folder, `hardware/<machine>/separation-basis.yaml`, and remove `accepted_by` and `accepted_on`.
2. Replace the inputs: `supply`, `working_voltage` (the top of your span, written with the number first, as `253 V rms`), `overvoltage_category`, `altitude_m`, `pollution_degree`, `material_group` and `environment`. Pollution degree is 3 unless your boards are protected against moisture, and the record says which. Where the enclosure protects the boards against moisture (keeps liquid water off them and allows no more than occasional, temporary condensation) the record credits pollution degree 2 only, never 1, and only on the stated conditions, which the record's header lists and the owner accepts with it. The credit stands on the enclosure; a conformal coat applied before the boards are energised is a supporting measure and is not itself the credit. The conditions are: the coat and its datasheet named in the fabrication notes and covering the gaps between mains pads, the protection stated as the enclosure's with the coat a supporting measure, a laminate comparative tracking index of at least 175, slots at least 1.0 mm wide (1.5 mm where a pollution degree 3 credit must survive), a bring-up humidity reading confirming no condensation while energised (with a fall back to pollution degree 3 as a fresh basis if it appears), and the whole record re-signed. A creepage reduced for a listed pair rests on its working voltage in normal operation plus a single-fault analysis recorded for that listing; the fault table is a comment of the record, which `board_check.py` does not read. The machine's record states an owner-accepted residual risk: its figures are single-sourced reproductions, and IEC 60335-1, IEC 60335-2-15 (appliances for heating liquids, the Part 2 that applies to a machine like this one), IEC 60664-1 and IEC 60664-3 are unread, with the conservative reading used wherever it is cheap. An adopter on another supply states their own residual risk in the same place.
3. Re-read the table rows your inputs select, in the sources the record's comments cite for IEC 60664-1 Annex F: the rated impulse voltage for your line-to-neutral voltage and overvoltage category (Table F.1), the clearance for that voltage at your pollution degree, with reinforced insulation read one step up and corrected for altitude above 2000 m (Table F.2 and its altitude factor), and the creepage for your working voltage, pollution degree and material group, doubled for reinforced insulation (Table F.4). Take the row at or above your working voltage; for creepage, where your working voltage lies between two rows, add one derived row at your working voltage instead, the linear interpolation between the two rows rounded up to 0.1 mm, its citation naming both rows, the arithmetic and the clause that allows it (IEC 60664-1:2007 clause 5.2.4), and whether the household-appliance standard allows it for its own table is yours to confirm before certification, the fallback being the higher row. If you read creepage between conductors for a working voltage below the supply's, add the functional band rows of your pollution degree and material group (the machine's record carries eight, 10 V to 320 V) with the band rule in their citation. Replace `table_rows` with only the rows you used, each with its citation and the inputs it was read at, and never copy a whole table: the standards are copyrighted.
4. Set `mains_to_low_voltage` to figures at or above the largest clearance and creepage your rows give. `board_check.py` compares them against those rows. Do the same for `mains_to_mains`: read the rows for basic insulation at conductors, at the terminals of a part (`location: terminal`) and, if the entry fuse clears a tracking fault downstream, for functional insulation, state `downstream_basis` for that, name your entry fuse's reference in `entry_fuse` (where `MAINS_ENTRY` is `present` it has a pad on a `Mains_Entry` net and a pad on a `Mains` net outside that class), and list in `held_at_reinforced` any pair of nets across a device whose bypass would defeat a safety function. In your design, set the project text variable `MAINS_ENTRY` to `present` or `none` and put the nets ahead of the entry fuse in the net class `Mains_Entry` as well as `Mains`.
5. List your barriers under `barriers`, with one `barrier_types` entry for each: its insulation (basic or reinforced), whether its low-voltage side is bonded to protective earth, what a person can touch beyond it, and the part or spacing that forms it. Judge each part's rating against the barrier it forms.
6. Write your own `accepted_exceptions`, or leave the key out. An exception is the owner's to sign and no one else's: a drafter, a tool or this repository's own record never signs one for you. Where a bought part's own geometry leaves less than a figure you signed between mains and low voltage, or between conductors at different mains potentials, you may accept the shortfall for the one pair of pads or nets concerned, writing the least distance you accept (`accepted_mm`, below the figure), your ground (`reason`) and the independent element that bounds the fault the shortfall could cause (`bounded_by`). Another pair involving the same part is not excused by it, and nor is the other constraint of the same pair. `board_check.py` judges each entry against the distance KiCad's own layout check reports (`spacing_exception`), prints each accepted one as an `ACCEPTED` line, and fails an entry that is unsigned, dated after the record's acceptance, relaxes nothing, names a pad or net the layout lacks or no shortfall uses. Where a connector's pin pitch leaves two of its plated holes closer than the plated-hole spacing rule of your board holds, and the connector carries slow signals only so that no fast signal crosses its strip, you may accept the shortfall with a `same_connector_pins` entry for that connector, writing its `pitch_mm`, the least distance you accept (`accepted_mm`, below the rule's figure), your ground and the independent element that bounds the fault; it excuses no pair of another part, nor of that connector at another spacing, and the check does not test your ground. Where a divider chain, a neutral-referenced group or a pair of mains nets with copper between them leaves a gap that carries less than the supply voltage, you may accept the shortfall for a set of nets with a `nets_a` entry (and `nets_b` for the other side), writing the `working_voltage_v` across the gap, your derivation of it in `reason`, and the least distance you accept (`accepted_mm`), which may be no lower than the creepage and clearance the record's functional band rows give for that voltage: the working voltage is the owner's assertion, and the check does not recompute it from the board's nets, so the band rows and your signature are the floor. It covers a pad, a track, a via or a zone of either list, never a net outside the `Mains` class, and never the pair across the open contact of the interlock relay. Adding or changing an entry needs a fresh acceptance of the record.
7. Sign it under your own identity: write your name in `accepted_by` and the date you accepted in `accepted_on` (YYYY-MM-DD), and commit the record. The commit is the audit trail. The drafter never fills these in for you, and a change to any figure, input or barrier needs a fresh acceptance.
